# tern-awui: how it works

The reference behind the [README](../README.md): what each feature reads and writes, the omp extension's bridge protocol, installer steps, build, tests, configuration and the security model.

## Features in detail

Paths below use `<omp dir>` for omp's data folder (`~/.omp/agent` by default; `TERN_AWUI_OMP_DIR`), `<notes dir>` for Tern's notes (`~/.local/state/tern/notes` on Linux; `TERN_AWUI_NOTES_DIR`) and `<config dir>` for tern-mobile's own files (`~/.config/tern-mobile` on every OS; `TERN_AWUI_CONFIG`); [Configuration](#configuration) has the defaults per OS.

- **List**: every Tern block, grouped by the git root (or folder) of its cwd, newest activity first within and between groups. A row shows the status (working: pulsing green, blocked: red diamond and tinted row, idle: ring), the title's Nerd Font icon (served as a PUA-only subset of `SymbolsNerdFont-Regular.ttf`), the `TAG:` prefix, a second line and the time in that status. The second line is omp's own recap for idle agents (the newest row of `session_recaps` in `<omp dir>/history.db`; italic, up to 2 lines, prefixed "Earlier:" when turns followed it), else the last prompt (scanned incrementally from the transcript). An omp session is known through its bridge connection, which reports its session id and its status live: *blocked* while an `ask` dialog or a tool approval waits, else *working*/*idle*; an idle session's time counts from its last transcript entry. Blocks without a bridged omp (shells, other agents) are terminals.
- **Collapsing projects**: tapping a project header folds its sessions away (▸/▾); the folded set is kept per device in `localStorage` (`tern-mobile:collapsed-projects`). A folded header still shows "N active" for its working or blocked sessions, and a filter shows matches inside folded projects too.
- **Hiding old sessions**: an eye button in the list header hides sessions whose time in their status is over a day (lit while on, with the hidden count beside the eye); kept per device in `localStorage` (`tern-mobile:hide-old`). Working, blocked, unseen and the open session always stay, as do blocks without a time (shells, notes), and a filter searches the hidden ones too.
- **Chat** (omp agents): the transcript tail from `<omp dir>/sessions/*/*_<id>.jsonl`, laid out like Tern's: prompts with an accent rail and `›`, assistant markdown full width, tool runs as one mono line (`▸ N tools · K failed  last intent`, tap to expand), and after each turn a right-aligned footer with duration, model and time that closes the turn. Body text is a step below white (bold stays white), with tight spacing inside a turn and extra space before each prompt. Each message hyphenates in its own language: `lang="hu"` when it contains ő/ű or more than 2 % accented vowels, else `lang="en"`. Tables are cards with row rules only, a small-caps header, faint zebra stripes and sideways scrolling; fenced code blocks are cards with their language in the corner. omp's figures render inline: ```` ```svg ```` blocks sanitized in place (with the `--fg`/`--accent`/`--c1`…`--c6` theme variables defined), ```` ```mermaid ```` blocks through mermaid (`securityLevel: strict`, dark theme), loaded as a separate chunk on first use; a diagram that fails to parse shows its source. Advisor notes (`custom_message` `advisor`) show as a card with each note's severity. A note with a `Key:` line shows the key, tap for its labeled lines (Evidence/Impact/Fix); the structure is an advisor-prompt convention, not omp's, so a note without `Key:` shows its own text as markdown, folded to two lines, whole after the tap.
- **Injected rules**: omp's time-traveling stream rules (TTSR) that fired mid-turn show as Tern prints them, in faded mono without a card: `• inject: <name>` and the first line of the rule's body; tap for the whole body as markdown. Consecutive injections merge into one block. Names come from `ttsr_injection` rows (`injectedRules`). Bodies come from the `developer` message that follows the tool result (`<system-reminder reason="rule_violation" rule="<name>">`, omp's `ttsr-tool-reminder.md` and `ttsr-warning.md`): the tag line and the preamble line are dropped. Interrupting rules (`ttsr-interrupt.md`) are never written to the transcript, so they show by name only.
- **Prompt actions**: like omp in Tern, hovering a prompt (or tapping it on a phone) shows its time, **Copy** (the prompt text to the clipboard) and **Rewind**. Rewind, after a confirm and only while the session is idle, goes back to before that prompt and puts its text back in the composer: the server submits `/tern-mobile-rewind <entry id>`, a command the extension registers, because only command handlers may call `navigateTree`. The chat shows only the active path of the session tree, walked back by `parentId` from the leaf the bridge reports (a rewind moves it without writing the file), else from the file's last entry, so abandoned branches don't appear.
- **Questions**: an open `ask` is a card with the options, their descriptions, the recommended one, multi-select boxes and *Other…* with a text field. A single single-choice question sends on tap. The server replays omp's ask-dialog keyboard (recommended row start, ↑/↓, Space, Enter, the Other prompt, the Review tab), after checking that the ask is still open.
- **Images**: pasted images and images that tools read (screenshots) show whole, at their own aspect ratio (at most 180 px high and 480 px wide, never upscaled), above the prompt's text or under the tool line; tap opens them full screen. The transcript stores most as `blob:sha256:<hash>`, served by `/api/blob/<hash>?type=<mime>` from `<omp dir>/blobs/<hash>` (PNG/JPEG/WebP/GIF only); small ones sit inline and go to the page as `data:` URLs.
- **Assistant screenshots**: Markdown images pointing to absolute local PNG/JPEG/WebP/GIF files are served through the authenticated blob API without changing the transcript. Each file is limited to 16 MiB; the server keeps up to 64 MiB or 128 images in memory and up to 4,096 authorized source paths. Evicted image bytes can be reloaded only from an unchanged, previously indexed file with the same content hash. Missing files, unsupported formats and final-file symlinks are not imported.
- **Images in prompts**: pasting an image into the composer, or picking one with the attach button (`<input type="file" accept="image/*" multiple>`, which on a phone offers camera, photos and files; non-image picks are skipped), shows it as a preview with a × above the text, up to 8 (omp sessions only). PNG/JPEG/WebP/GIF under 3 MB go as they are; anything bigger or of another type is scaled to a 2048 px long edge and sent as JPEG. On send, the text and images reach omp as one user message through the bridge (`send` → `pi.sendUserMessage`: a new turn when idle, a steer while working), and the desktop draft is cleared. Shells and sessions without the bridge refuse images and show no attach button.
- **Screen**: omp agents: `tern capture --surfaces`, the last 160 lines of the main region (transcript text and progress; not overlay dialogs), reached through **Raw** at the start of the key bar (⌨); the button then reads **Chat** and switches back. Plain terminals: `tern capture --html`, one screen with colors, sanitized to `<pre>`/`<span style>`, polled every 450 ms; prompt glyphs come from the bundled symbols font. In terminals the composer types live onto the shell's own line (each edit becomes Backspaces plus new text, autocorrect off), the soft keyboard's Enter presses Enter, and the key bar is open by default, so interactive tools like `op`/fzf work: type to filter, ↑/↓, ⏎. Tab completion changes the line behind the composer; any key-bar key clears the composer.
- **Notes and files**: file blocks (`file` in `tern ls --json`) open read-only. Tern notes (`note:<id>`) are read from `<notes dir>/<id>.md` and rendered as markdown; other files (any absolute path) as text, first 512 KB. Files are syntax highlighted by extension (or bare name, such as `Makefile`), and so are fenced code blocks in opened markdown files, by their language; highlight.js with its common languages loads as its own chunk on first use. Unknown languages and files over 256 KB stay plain. Chat code blocks are not highlighted.
- **New omp in any project**: **+ omp** in the header lists folders, filterable, with already-open ones marked and paths under the home folder shown as `~` (either separator); a tap opens an omp tab there and jumps into it. By default the folders are the cwds of the open Tern blocks and of past omp sessions (the `cwd` in each transcript's `session` header row), most recently used first: an open block at its last omp activity, a session at its transcript's last write, open blocks without omp activity last. Each folder shows once, under its most recent spelling: trailing separators are dropped and folders are told apart by device and inode, so a case-insensitive file system's `Code` and `code`, or a symlink and its target, are one entry. Existing folders only. `TERN_AWUI_PROJECTS` names a command whose output (one absolute folder per line) replaces that list.
- **Composer**: sends the prompt and Enter. ⌨ opens the key bar (Esc, ^C, arrows, Enter, Tab, ⇧Tab, Space). The model chip shows the model, effort and a non-standard tier; ⌖ focuses the block on the desktop, **+ omp** opens a new omp tab in the project.
- **Model picker** (tap the model chip): a bottom sheet on phones, a centered 560 px panel on desktop browsers. On top, **Effort** (the current model's thinking levels, from omp's `getSupportedThinkingLevels`) and **Priority** (its service tiers: Standard, Flex, Fast = `priority`; `pi.setServiceTier` for the model's family, session-only). Below a search field: the Ctrl+P roles first (`cycleOrder` → `modelRoles` from omp config, a pick applies the role's model and thinking), then the last 6 models picked on this device (`localStorage` `tern-mobile:recent-models`), then every chat model omp has credentials for (`modelRegistry.getAvailable("chat")`, ~1,700 here, cached 5 min by the server), folded by provider. A search matches every word against name and `provider/id`, the whole query in the name ranking first. Rows show the context window, $ per million in·out, reasoning and vision. The extension imports omp's `@oh-my-pi/pi-ai` shim with a literal specifier (omp's loader rewrites only literals; `omp-extension/pi-ai.d.ts` declares it for tsc).
- **Command hints**: while the text ends in a `/command`, `/skill:name` or `@path` token, the list above the composer shows omp's own autocomplete for it (built-in and extension commands, skills, prompt templates, files), with descriptions. A tap applies the suggestion in omp (`applyCompletion`), which also updates the desktop draft. Needs the bridge: the extension captures the editor's provider through `ctx.ui.addAutocompleteProvider` and answers `complete`/`apply` requests (`/api/blocks/<id>/complete`, `/completion`).
- **Context gauge**: like omp's own composer, the composer's top border is the context-window gauge of bridged omp sessions (`ctx.getContextUsage()`, sampled every 2 s by the extension): the used part in accent, the percent riding just past it, the window size at the right end; the percent turns red past 100 %. A tick marks where auto-compaction fires, computed by the server from `omp config` (`compaction.enabled`, `thresholdTokens`, `thresholdPercent`, `reserveTokens`, as omp's `resolveThresholdTokens` does; per-model thresholds are not read). The speculative-compaction marker is not drawn.
- **Stop**: while the agent works and the composer is empty, the send button turns into a stop square: `ctx.abort()` through the bridge (Escape without it). With text typed, it sends the text as a steer.
- **btw**: bare `/btw` opens a read-only view of the main session's saved native omp btw history, newest first, with questions, answers, statuses and follow-up turns. It reads `<session file without .jsonl>/btw-history/entry-<id>.json`; reopening refreshes the list. Viewing history makes no model call and does not open a desktop dialog. `/btw <question>` keeps the existing web side-turn behavior (`ctx.runEphemeralTurn`, no tools): the answer streams into a dismissible card above the composer. These web cards are transient, not saved native history. Successfully handled commands clear the mirrored draft; failed history requests leave the command available for retry.
- **Git branch**: the session header shows the checked-out branch of the block's cwd (`git branch --show-current`, short sha when detached, cached 10 s per cwd); nothing outside a repo or for file blocks.
- **Badge and haptics**: the installed app's icon counts unseen updates: sessions that finished a turn or started waiting on you since the phone last opened them. Like Tern's tab icons, such a row's icon turns green (finished) or red (waiting on you) and its title goes bold; omp sessions without a title icon yet show Tern's `π` fallback, and only rows with no icon at all get a dot. Opening the session, the agent working again, or the pane closing clears its update. Set from the stream, and by the service worker from each push's `badge` count while the app is closed. Sends, stops, answers, picks and key-bar taps buzz briefly (`navigator.vibrate`, Android only).
- **Close**: the red ✕ in a session's header runs `tern close` after a confirmation (it closes the block on the desktop too; the dialog warns if the agent is working or waiting on you), then returns to the list.
- **Extension check**: the app tells you when omp's extension isn't the one this checkout ships, and how to fix it. The installed file, `<omp dir>/extensions/tern-mobile.ts` (`~/.omp/agent` unless `TERN_AWUI_OMP_DIR`), is fine as a link to the checkout's `omp-extension/tern-mobile.ts` or a copy with the same content; otherwise it is *missing* (a dangling link included), *stale* (a copy that differs: a Windows install after `git pull`) or *foreign* (a link to another file). The server rechecks it on every list rebuild and re-reads it only when its or the checkout file's inode, mtime or size changes. Unless it is fine, a banner tops the session list (phone and desktop sidebar) with what's wrong and the fix to copy: `cd <checkout> && bun install.ts` (PowerShell: `cd <checkout>; bun install.ts`). Each bridged omp reports its extension's `build`, the first 16 hex digits of the sha256 of the file omp loaded (read once at load through `import.meta.path`; omp imports extensions from their real path, so a symlinked install reads the checkout's file), and its bridge `protocol` (2). A session with another build than the checkout's file, or a lower protocol, runs an *older* extension; a higher protocol means the server is the older side (*newer*). Such rows get a `!` mark, the list header counts them in a `! N` chip, and the session shows a notice under its header. Older: **Reload** (after a confirm, only while idle) submits omp's `/restart`, which restarts omp in its pane with the same flags and resumes the session, loading the installed extension. omp 18.2.0 and later have it (18.0.3 doesn't); the server asks each older session's omp through its own autocomplete. An omp without it gets `omp --resume <session id>` to run after quitting it. omp has no command that reloads extensions in place (`/reload-plugins` reloads skills, commands and MCP, not extension modules). When the installed file is not fine either, the notice says to reinstall first and offers no Reload. Newer: `cd <checkout> && git pull && bun install.ts`. Sessions without a bridge (terminals, notes) are never flagged, and an extension that couldn't read its own file reports no build and is judged by protocol alone.
- **Leaving**: on the list, the first back gesture only shows "Press back again to exit"; a second one within 2 s leaves the app. The list keeps a guard history entry for this. In a session, ‹ and the back gesture both return to the list; in a subagent screen, to the screen it was opened from (its session or the subagent list). ‹ pops history when that screen is the one below, and replaces the entry otherwise (a deep link, a notification), so back never reopens what it left.
- **Desktop browser**: at 1000 px and wider the list stays in a 360 px left sidebar (the open session highlighted). The session uses the remaining space with a centered content column up to 1100 px wide, shared by its transcript, header, composer and extension notice. Narrower windows retain the existing gutters; mobile layout is unchanged. All of it lives behind one `@media (min-width: 1000px)` block and the `useWide()` switch in `App`. The back-to-exit guard and the session's ‹ are phone-only; subagent screens keep their ‹, which leads back to the session.
- **Sidebar rail**: the "tern" brand in the list header is the minimize button: on hover or keyboard focus `«` replaces the word in the same grid cell, so the header doesn't shift. It or Ctrl+\ (⌘\; Ctrl+B is Firefox's bookmarks sidebar) minimizes the sidebar to a 56 px rail, `»` or the shortcut expands it; `App` keeps the choice in `localStorage` (`tern-mobile:sidebar-rail`) and `Home` renders the rail when `rail` is set. One round button per session links to it, showing the title's Nerd Font icon, else the block's tag (first 3 letters), else two letters of the title (`railGlyph`; omp's π alone would make sessions look the same). The ring takes the status colour, the unseen dot sits on its corner, the open session gets an accent bar, and the tooltip is the title and the row's subline. Project labels (first 4 letters) toggle the same collapsed set as the full list and show the active count when shut. The header keeps the connection dot, the blocked count and the bell, the foot the new-omp `+`. The rail ignores the filter typed in the full list; hiding old sessions still applies. The list header's counts are the rows' status dot (smaller, without the pulse) and a number each, with "N blocked/working/idle" as their tooltip and accessible name.

Updates arrive over one SSE stream per screen, pushed rather than polled. The server follows `tern events` (any event except the `client_*` pair every CLI call logs), bridge changes (connect, disconnect, status, model, thinking, tier, context, session id, protocol, build, caps) and writes to `<omp dir>/history.db` (recaps); each batch (150 ms) rebuilds the list once and every open stream rechecks it. The open transcript or file is followed with a watch on its folder. Only terminal screens are still polled (Tern has no output event): every 450 ms for shells, 1.2 s for an omp's Raw screen, and only while one is open. A 15 s recheck backs up missed events.

The app holds a stream only while it is visible: 10 s after it is hidden (another app, screen off, a background tab) the stream closes and nothing flows; it reopens when the app comes back. With no phone watching, sessions also send no live text and count as unseen again. Closed or hidden, only Web Push notifications reach the phone.

- **Live text**: while a phone has a session open, the extension forwards the assistant message omp is writing (`message_update`, text parts only, at most every 200 ms) and the phone shows it below the transcript as it grows. When the message ends, the copy stays until the transcript write brings the final one, so nothing flickers. Sessions nobody watches send nothing (the server tells each omp with `watch` on/off).
- **Queued steers and follow-ups**: prompts sent while the agent works show below the transcript until omp takes them: `↳` for a steer, `→` for a follow-up held until the turn ends. The web composer's `→` button, Ctrl+Enter or Ctrl+Q sends an explicit follow-up through `pi.sendUserMessage(…, { deliverAs: "followUp" })`. For interactive desktop input beginning exactly with omp's `->` or `=>` queue syntax, the extension removes that prefix from the displayed text and reports a follow-up; leading whitespace, embedded arrows and RPC text are not interpreted as queue syntax. This changes only the display, not the input event or delivery. Numbered batches remain one locally tracked group. Extensions cannot read omp's actual queue, so tracked prompts clear when `ctx.hasPendingMessages()` becomes false. Desktop Ctrl+Q without a prefix still appears as `↳`, because the input event does not expose the submitting key. Queue updates travel in bridge state and `queued` SSE events.
- **Tool intents**: a tool line shows the call's `i`; eval calls show their `title`; with neither, the first line of `command`/`path`/…/`code`.
- **Working row**: while a session works, the bottom of the chat shows omp's own working row: a braille spinner, the turn's running time (`31.6s` in tenths for the first minute, then `3m 05s` each second) and what the turn is doing, in mono with an accent highlight sweeping over it (no animation under `prefers-reduced-motion`). The extension reports `run`: `since` from omp's `agent_start`, and `intent`, the `i` argument of the tool call omp is streaming (`message_update`), then the label omp resolves when it runs (`tool_execution_start`'s `intent`, which falls back to the tool's own, like eval's "running javascript"); "" shows as "Working…". It is null while idle and after `agent_end`. The server sends it only to the open session's stream (`run`, also on open), and clears it when the pane's bridge is replaced or lost. Without it (older extensions) the row counts from the status change.
- **Todo lists**: a tool line that ran `todo` carries omp's list as that call left it (`details.phases` of the tool result; the newest per tool group). The newest list in the chat shows every task: per-phase headings when there are several, `✓` done (faded), `▸` in progress, `○` pending, `!` blocked with its reason. Older ones collapse to one line (`done/total`, blocked count, the current task); a tap toggles either.
- **Subagents and background jobs**: the extension samples `ctx.getAsyncJobSnapshot()` once a second and reports the running jobs (id, type, label, agent name, start). A row with jobs gets a line like "2 subagents · 1 background job"; the session shows each one under the transcript (`⑂` subagent, `⧗` other job) with its name and run time. Running `task`/`eval` subagents keep the session *working* even while its own turn has yielded to wait for them, so the list and "finished" notifications don't treat it as done; a backgrounded bash job (a watcher, a server) doesn't.
- **Subagent transcripts** (read-only): omp writes each subagent's transcript next to the session's, in the folder named like the session's file without `.jsonl` (`<stamp>_<id>/<AgentName>.jsonl`; the job's agent name is the basename). Tapping a running subagent in the `⑂` strip opens its chat (`#/b/<block>/sub/<name>`); while any subagent runs, **Subagents (N)** under the transcript lists all of them, finished ones too (`#/b/<block>/sub`): running first, then newest activity, each with its result (else its last reply, else its last tool intent), message count and age. Once every subagent has finished the entry goes away (the list route still works). A subagent's chat is the session's chat renderer (tools, todo lists, images, markdown) without composer, prompt actions or answerable questions, under a header with its name, running/finished and the parent session; its prompts, written by the parent agent, render as Markdown with every stretch drawn open; the text it hands back with `yield` (`data.result`) shows as its final reply. It updates as the file grows (`/api/stream?block=<id>&view=chat&sub=<name>`; the list: `view=subagents` or `GET /api/blocks/<id>/subagents`). Names must be plain (`[A-Za-z0-9][\w.-]*`, so no paths, dot files or `__advisor.<model>.jsonl` advisor transcripts; anything else is a 400), symlinks are ignored, and `.md` results and `.log` tool output aren't subagents. Subagents show only while the session's omp is bridged (its session id finds the folder).
- **Table charts**: like omp in the terminal, a markdown table with numbers gets a bar chart under it (`web/charts.ts`): one panel per measure, one colored bar per option, each panel scaled on its own. Cells are read as number, range (`0.23–1.04 MB`, plotted at its middle) and unit (bytes, time, %, `$`, counts; a trailing parenthetical is ignored). Rows are the measures when each row keeps one unit and the columns mix them, else the columns are. The best value is marked only when the measure's name points one way (time, size, cost, errors… lower; accuracy, reusable, throughput, revenue… higher; "error rate"-style names that match both, and names that match neither, get no best). The headline is the "X is best on …" sweep when one option wins at least two measures; omp's model-picked headlines are not reproduced.
- **Stretchtext replies**: for omp sessions running the `stretch.ts` extension ([pro-vi/cc-stretch](https://github.com/pro-vi/cc-stretch) for omp; not part of tern-awui), where the model writes `{{short|long}}`. A reply shows each short form as a dotted-underline link (`#stretch/open/<i>`, never routed); a tap grows the long form in place over up to 700 ms and puts a `«` after it, which closes it and everything nested in it. Live text shows short forms only; btw answers show every long form. The transcript gives such a reply part its block id, `<message timestamp>.<content index>` as stretch.ts names it. When the pane's omp runs stretch.ts, the open state is shared both ways: the extension reports stretch.ts's open keys per block in its snapshot (`stretch`, through `globalThis[Symbol.for("omp-stretch")].bridge`, version 1), the server streams changes as `stretch` events, and a tap posts `/api/blocks/<id>/stretch`, which the extension applies with the bridge's `setOpen`, so the pane grows it too and the next prompt's read note counts it. `/stretch off` in omp (`off: true`) draws every long form. Without stretch.ts (or in a subagent's chat) open stretches are local to the page.
- **Recaps in the chat**: omp writes an idle recap to `history.db` (`session_recaps`) once the terminal has sat idle for `recap.idleSeconds`, and prints it under the turn with `※`. The chat shows every recap of the session the same way: `readChat` reads them all (`querySessionRecaps`) and `withRecaps` merges them by time, so each lands after the last entry before it was written (its whole-second `created_at` counts as the end of that second) and before the next prompt. Recaps older than the chat's first shown entry are dropped with the part of the transcript left out. A recap arrives without a transcript write, so the chat stream's etag includes the session's newest recap, which the history.db watcher already refreshes. A recap of a branch rewound away still shows at its time, before the prompt that followed the rewind.

## Draft mirroring (omp extension)

`omp-extension/tern-mobile.ts`, symlinked to `~/.omp/agent/extensions/tern-mobile.ts`, runs in every omp started in a Tern pane (`$TERN_PANE`). The installer writes `~/.config/tern-mobile/bridge.json` with the local WebSocket endpoint and absolute bridge-token path, so omp started independently finds custom ports and config directories. Without valid discovery settings it uses `ws://127.0.0.1:4380/bridge` and the default config folder. Explicit `$TERN_AWUI_BRIDGE` and `$TERN_AWUI_TOKEN_FILE` override discovery; `$TERN_AWUI_CONFIG` overrides the discovered token directory. Restart existing omp sessions after changing these settings. The extension:

- polls `ctx.ui.getEditorText()` every 100 ms and sends the draft, model, thinking level and idle state when they change;
- applies `set` (phone keystrokes → `setEditorText`), `model` (`provider/id[:thinking]` → `pi.setModel` + `setThinkingLevel`), `thinking`, `tier` (`pi.setServiceTier`), and answers `models` with the catalog;
- reports the current model's thinking `levels`, `tiers` and active `tier`;
- while watched, sends the message being written (`live`) and its end;
- reports the running turn (`run`: its start and the current tool call's intent, null when idle);
- reports the prompts waiting in omp's queue (`queued`) and the session's leaf entry (`leaf`, `-` for none);
- reports stretch.ts's open stretches (`stretch`, null without it) and applies `stretch` (open or close one in the pane);
- reports its bridge `protocol` and `build` (the sha256 prefix of its own file), so the app can flag a session that loaded another version (see *Extension check*);
- registers `/tern-mobile-rewind`, which the phone's Rewind submits.

The phone shows a green dot by the model chip while mirroring. Its own edits win for 800 ms over echoes from the desktop; live keystrokes are last-writer-wins on both sides. A draft write may carry the draft it replaces (`expected`, used by the phone's clear after a handled command); the extension refuses it ("draft changed") when omp's editor holds something else by then. Keystrokes don't carry it: the server's copy lags omp's editor by up to one 100 ms poll, so a guard would refuse the phone's own fast typing. Submitting always sets the draft to the phone's text, waits for omp's acknowledgment, then sends Enter, so slash commands work as typed. An image or follow-up `send` clears omp's editor only when it still holds the draft the server last saw.

omp loads extensions at startup: sessions started before the extension was installed don't mirror until restarted, and sessions started before it changed keep the version they loaded (the app flags them). Without the bridge, the composer types the prompt with `tern send` and the model sheet can only cycle (Ctrl+P).

Tern's CLI can't read a pane's editor (`tern capture` returns only the main surface region), and the plugin API's `surface()` returns nothing for hidden panes, so the draft is read from omp.

## Notifications

The bell in the list header turns on Web Push for that device (service worker `sw.js`, VAPID keys in `~/.config/tern-mobile/vapid.json`, subscriptions in `push.json`, both mode 600). It has four looks: slashed (off, or blocked in site settings), slashed in red (stopped: Android took notifications away from the installed app, see below), dimmed and pulsing (pending: asking for permission, subscribing, or waiting for the server to store the subscription; taps are ignored), and a green dot (on: the server confirmed it). The choice is kept per device in `localStorage` (`tern-mobile:push`); on every load a device that chose *on* checks its subscription, silently makes a new one if the browser dropped it or it belongs to another VAPID key, and re-sends it to the server, so updates and reloads don't turn notifications off. Bridged omp sessions trigger them:

- **Needs you**: the status turns *blocked* (an `ask` or a tool approval); the body is the question.
- **Finished**: *working* → *idle* that stays idle for 3 s; the body is the start of the last reply.

One notification per session (a newer one replaces it); tapping opens that session. A fresh bridge connection (restarted omp) never notifies. Payloads are end-to-end encrypted, but they travel through the browser's push service (FCM for Chrome), which also sees the VAPID subject: `mailto:` the first allowed login when it is an address, else a placeholder (`TERN_AWUI_VAPID_SUBJECT` overrides). Subscriptions the push service reports as gone (404/410) are dropped. The service log names each removal: `push: … reported a subscription gone`, or `push: a device on … removed a subscription` when a device unsubscribes one it had registered (turning notifications off, or the service worker retiring a subscription the browser replaced).

A device that chose *on* repeats the load-time check whenever the app returns to the foreground or the network comes back, because an installed app can stay open in the background for days while the server prunes or loses its subscription. A failed recheck keeps the bell on and tries again next time. A failed first check (the server restarting during an update, say) retries on its own after 5 s, doubling up to once a minute, until the server takes the subscription; a retry that comes due while a tap on the bell is still working waits for it. If the browser forgot the notification permission (it reads *default* again), the device can't ask without a tap, so the first tap anywhere in the app asks once more and subscribes when granted, except in the stopped state below, where only the bell asks. A dismissed prompt is not asked again on later taps until the permission has been granted and lost again. A toggle made during a recheck wins. Turning on also asks the browser to keep the origin's storage (`navigator.storage.persist()`), which holds the choice and the subscription; the browser may refuse, and the app goes on without it. When the browser replaces a subscription on its own (`pushsubscriptionchange`), the service worker registers the new one, so this works with the app closed.

On Android, an app installed from Chrome is its own Android app (a WebAPK) with its own notification permission. Without that permission, Chrome resets the site's permission to *default* and drops the push subscription each time the app opens from its icon, and `Notification.requestPermission()` shows nothing and never settles: Chrome hands the prompt to another installed app of the same host (seen with Chrome 155 on Android 16). The bell therefore stops waiting after 10 s and counts the request as *default*, leaving a stopped bell stopped. An answer that still comes later counts: a grant with no newer tap on the bell records the choice and subscribes. A permission request answered *denied*, or a tap on a blocked bell, shows where to allow notifications: App info → Notifications for the installed app, the site's permissions in a browser tab. A request answered *default* (a dismissed prompt) shows nothing, except in the installed Android app, where Android blocking the prompt looks the same, so the message mentions App info. The page can't open those screens itself: Chrome follows `intent:` links only to activities marked browsable, and Android's settings screens aren't.

No web API shows that Android permission: `Notification.permission`, `permissions.query` and `pushManager.permissionState` can all read *granted* while it is off, because a request from the bell may be answered with the permission of another installed app of the same host. Notifications then work until the next launch from the icon. The app goes by what that launch leaves behind instead: in the installed Android app, a device that chose *on* that finds the permission back at *default* and no subscription shows the bell **stopped** (slashed, red, "Notifications stopped: Android blocks this app") and remembers it (`tern-mobile:push-app-blocked` in `localStorage`). In that state a tap anywhere doesn't ask again (the request would hang or borrow again), only the bell does, and a grant from it turns notifications on with a warning that they'll stop at the next launch unless App info allows them. Only turning notifications off clears the mark: no page load proves the Android permission came back, since a page opened from a notification or running on a borrowed grant looks like a healthy launch. The stopped look itself is decided afresh at every check.

## Requirements

On every OS: [Bun](https://bun.sh) (1.4 tested), Tern with its `tern` CLI on `PATH` and omp (`omp` on `PATH`). The installer also needs Tailscale logged in with MagicDNS and HTTPS certificates enabled for the tailnet (Tailscale Serve needs both); without Tailscale, run the server yourself (end of [Install](#install)). git is optional: without it projects group by folder and no branch shows. Building needs nothing beyond Bun (see [Build](#build)).

- **Linux** (Arch, verified): a systemd user session. The service runs while you're logged in; `loginctl enable-linger $USER` keeps it running after logout and starts it at boot.
- **macOS** (verified on macOS 26, Apple Silicon): launchd. If `tailscale` isn't on `PATH`, the installer uses the App Store / standalone app's CLI at `/Applications/Tailscale.app/Contents/MacOS/Tailscale`.
- **Windows** (not run): Task Scheduler (`schtasks`), Windows Script Host (`wscript.exe`) and PowerShell, all built in. No admin rights: the task runs as you, at your logon. The extension is copied, not linked (symlinks need Developer Mode), so re-run the installer after updating the checkout; the list's banner says when the copy is stale.

## Install

```bash
bun install
bun run install-service           # = bun install.ts [--port N] [--dry-run]
bun install.ts --uninstall        # [--dry-run]
```

`install.ts` installs a per-user service for this checkout. In order, it:

1. builds `dist/` (`bun build.ts`);
2. puts the omp extension into `<omp dir>/extensions/tern-mobile.ts` (`~/.omp/agent` unless `TERN_AWUI_OMP_DIR`): a symlink to `omp-extension/tern-mobile.ts` on Linux and macOS, a copy on Windows;
3. writes the service, with the absolute paths of bun and the checkout, a `PATH` starting with the folders of `tern`, `omp` and bun, the port and the allowed logins, and starts it (a re-run restarts it with the new settings):
   - Linux: `~/.config/systemd/user/tern-awui.service` (a real file; a symlink left there is replaced), `systemctl --user daemon-reload`, `enable`, `restart`; before writing it, the pre-0.3 `tern-mobile.service` is stopped, disabled and removed (uninstall removes it too);
   - macOS: `~/Library/LaunchAgents/dev.tern-awui.plist` (`RunAtLoad`, `KeepAlive`, log in `~/Library/Logs/tern-awui.log`), `launchctl bootout` + `bootstrap gui/<uid>`;
   - Windows: a launcher `tern-awui.vbs` in the config dir that runs bun with no window and restarts it 3 s after it exits, and a scheduled task `tern-awui` that starts it at your logon (`schtasks /Create /XML`, then `/Run`);
4. runs `tailscale serve --bg --https=<port> http://127.0.0.1:<port>`;
5. prints the app's URL: `https://<this machine's tailnet name>:<port>/`.

The allowed login is the device's own Tailscale user (`tailscale status --json`) unless `TERN_AWUI_ALLOW` is set; the installer refuses to publish without one. `TERN_AWUI_HOSTS` is written as the device's tailnet name (Tailscale Serve keeps the browser's `Host`), followed by any names `TERN_AWUI_HOSTS` held when the installer ran. `TERN_AWUI_PORT` (or `--port`) and any of `TERN_AWUI_CONFIG`, `TERN_AWUI_OMP_DIR`, `TERN_AWUI_NOTES_DIR`, `TERN_AWUI_PROJECTS`, `TERN_AWUI_VAPID_SUBJECT` set when the installer runs are written into the service. `--dry-run` prints every file it would write (with its content) and every command, and changes nothing. `--uninstall` stops and removes the service, the extension link or copy (a link to another checkout's extension stays) and the serve entry; the config dir (tokens, VAPID keys, subscriptions) stays.

Relative config, omp and notes directories, and a `TERN_AWUI_PROJECTS` path containing a separator, are resolved before installation. The installed port is read back from `bridge.json` (when it belongs to this config dir): a re-install on another port turns the old `tailscale serve` port off, and `--uninstall` without `--port` or `TERN_AWUI_PORT` uses it. Uninstall removes bridge discovery only when it still matches this installation; missing optional cleanup commands are reported without stopping the remaining cleanup.

**Opening it.** Open the printed URL on the phone, signed in to Tailscale as an allowed login; in Chrome on Android, ⋮ → *Add to Home screen* installs it. Any device of an allowed login on the tailnet gets in, so there is nothing to pair.

omp loads extensions at startup, so omp sessions already running don't bridge until restarted (`/restart`). The app flags bridged sessions running an older extension and offers Reload (omp's `/restart`) where omp has it.

Without the installer (no Tailscale, or for development), run the server directly. Without `TERN_AWUI_ALLOW` it has no login check, so everything that can reach the port gets a shell (see [Security](#security)):

```bash
bun run build && TERN_AWUI_PORT=4381 bun server.ts
```

## Build

`bun run build` (`bun build.ts`) bundles `web/app.tsx` into `dist/` and copies the static files from `web/` and the prebuilt binaries from `assets/`; it needs no other tools. `assets/` is committed:

- `icon.svg`: the app icon (a "T" with a green dot) as a full-bleed tile.
- `icon-v2-32.png`, `icon-v2-180.png`, `icon-v2-192.png`, `icon-v2-512.png` (rounded corners) and `icon-v2-maskable-512.png` (the full tile, its mark inside Android's safe circle): favicon, Apple touch icon, PWA and notification icons rendered from it. The `v2` in the names makes browsers fetch new files when the icon changes.
- `symbols.woff2`: the private use areas of Symbols Nerd Font (`SymbolsNerdFont-Regular.ttf`, Nerd Fonts 3.5.1) subset by `pyftsubset`, for the Nerd Font icons in pane titles; its license is `assets/LICENSE-nerd-fonts-symbols` (SIL OFL 1.1 for the fonts, MIT for Nerd Fonts' code).

Build output is prepared in a temporary sibling directory. Compilation or missing-asset failures leave the previous `dist/` intact; replacement happens only after the new files are ready.

Each build gets an id, a hash of its files: `dist/build-id`, also baked into the bundle. Rebuilding unchanged sources keeps the id. The server serves `dist/` from disk, so a rebuild needs no restart. It watches for the new `dist/` and sends its id with the list (`state.app`). An open page built from another id reloads itself, once its composer holds no unsent text or images.

`bun run assets` (`bun assets.ts`) regenerates them after changing the icon or updating the font. It needs ImageMagick's `magick`, `pyftsubset` (fonttools with brotli) and the font at `/usr/share/fonts/TTF/SymbolsNerdFont-Regular.ttf` or `TERN_AWUI_SYMBOLS_FONT`. If `optipng` is installed, it and `bun docs/screenshots.ts` shrink the PNGs losslessly (`-o7 -strip all`); without it they write unoptimized PNGs.

## Tests

```bash
bun test
bun test --coverage
bun run typecheck
bun test test/e2e
```

The unit suites cover parsing, security boundaries and UI behavior. Preact tests render the chat, list, session and model-picker modules in happy-dom, including markdown, prompt actions, model selection and read-only subagents.

GitHub Actions (`.github/workflows/ci.yml`) runs the typecheck, the full suite with coverage including the browser tests (a fresh Playwright headless shell, required there rather than skipped) and the build on Linux. macOS and Windows jobs run the platform-dependent suites (`lib/`, `web/`, the extension and the installer, including the PowerShell checks on Windows) and the build; they report without blocking until they have passed natively.

Releases: new entries go under `## Unreleased` at the top of `CHANGELOG.md`. To release, rename that heading to `## X.Y.Z (YYYY-MM-DD)`, set `version` in `package.json`, commit as `X.Y.Z`, then push an annotated tag `vX.Y.Z` (`git tag -a vX.Y.Z -m "tern-awui X.Y.Z"`). `.github/workflows/release.yml` then publishes a GitHub release whose notes are that changelog section; a missing or empty section fails the run instead of publishing.

Server integration tests call `startServer({ env, home, dist, sendNotification })` in-process, so `bun test --coverage` measures `server.ts`. Each sandbox uses a temporary HOME, fake `tern` and `omp` executables, a random loopback port and fake bridge WebSocket clients. Push delivery is injected where tested. The harness can also run a subprocess for process-level checks. Installer tests exercise `main()` with temporary files and fake commands, covering install, uninstall, dry runs, configuration and command failures. macOS and Windows installer paths are tested as plans, not native service installations.

The browser suites use `playwright-core` with headless Chromium at phone size, 412×900, and desktop size, 1400×900. Set `TERN_AWUI_CHROMIUM` to its executable, or use an existing `~/.cache/ms-playwright/chromium_headless_shell-*/chrome-headless-shell-linux64/chrome-headless-shell`; the newest cached revision wins. The suites skip if neither exists. They do not download a browser.

Browser tests run `build.ts` in a temporary checkout directory and serve its temporary `dist/`. They do not rebuild the live app's assets. Requests carry the allowed `tailscale-user-login` header, service workers are blocked, and page requests cannot leave the sandbox server. Tests assert rendered content, navigation and the actions received by the fake bridge and CLI, including drafts, sends, asks, models, rewind, live text and subagents. They never connect to the live `tern-mobile` service or real Tern panes. Chromium execution is outside Bun's coverage instrumentation, so browser-exercised UI lines do not contribute to the Bun coverage report.

`TERN_AWUI_LIVE=1 bun test omp-extension/tern-mobile.live.test.ts` opts into the real omp bridge test. It uses temporary HOME/config directories and a dummy credential, without model prompts; explicit opt-in fails if omp is missing. PowerShell process-selection tests skip when `pwsh` is unavailable. Permission-denied filesystem scenarios skip when run as root. These skips do not verify native Windows services, macOS services or real push delivery.

## Security

This is a remote shell into the desktop, and it has **no authentication of its own**. Access control belongs to whatever stands in front of the port; the server only makes sure that "loopback only" means that, and offers one optional identity check for Tailscale.

Out of scope, by design:

- **Who reaches the port.** The server listens only on `127.0.0.1`. Keeping it on loopback, or publishing it through Tailscale Serve (what the installer does), Cloudflare Access, an SSH tunnel or similar, is the user's choice and the user's responsibility. **Never enable Funnel** or forward the port publicly.
- **Other local accounts.** Any account on the machine can connect to `127.0.0.1` and set any header. The machine must be single-user.

Built in:

- **Host check (DNS rebinding).** Every request, the bridge's too, must name `localhost`, `127.0.0.1`, `[::1]` or a `TERN_AWUI_HOSTS` entry in `Host` (any port, case and a trailing dot ignored); anything else, or no `Host`, gets 403. Without it, a web page that rebinds its own domain to 127.0.0.1 would count as same-origin in the user's browser and could set every header below.
- **Same-origin POSTs.** POSTs require an `x-tern-mobile: 1` header; a cross-site page can't send it without a CORS preflight, which the server never approves. Key names are allowlisted.
- **Bridge token.** `/bridge` refuses requests carrying a Tailscale login header (anything proxied from outside) and requires the bridge token (`<config dir>/bridge-token`, mode 600). Browsers can't set that header on a WebSocket, so no page can pose as an omp session.
- **Optional Tailscale login allowlist.** With `TERN_AWUI_ALLOW` set, every request (the API, its stream and the app's own files) must carry an allowed `Tailscale-User-Login`, else 403; tagged devices get no login header, so they are refused. The header is trusted as-is: it means something only when Tailscale Serve (or a proxy that overwrites it) is the only way in. Without `TERN_AWUI_ALLOW` there is no login check and the startup log says so.
- tern can report errors with exit status 0, so non-WARN stderr counts as failure and is returned to the phone. Typed text goes after `--`, so text like `--help` is typed, not read as tern's flags.
- Agent markdown goes through DOMPurify. Only `http(s)` and `mailto` links are kept, and raw HTML is shown as text.
- Responses carry a Content-Security-Policy (`default-src 'self'`, images also `data:`/`blob:`, inline styles allowed for mermaid): images agent markdown points to on other sites are never fetched, so a prompt injection can't leak data through an image URL.
- Texts sent for a block (prompts, drafts, completions) are capped at 1,000,000 characters; Bun closes bridge frames over 16 MB.

## Limits

- It is not a terminal emulator. Full-screen TUIs (vim, htop) only work through the screen capture and the key bar.
- Status, chat, model picks and images need the omp to be connected to the bridge: omp sessions started before the extension's current version show as terminals until restarted (`/restart`).
- Features the session's omp lacks (the extension reports them as `caps`) are turned off in the app, and the server refuses Rewind, the model catalog and tier changes for them with 409. An extension without `caps` (before versioning) is taken to support everything, as before.
- Linux and macOS have run this; Windows hasn't. omp's directory on macOS is verified; Tern's notes folder on macOS and both locations on Windows follow their sources (omp's directory resolver, the strings in the tern binary) and are unverified. `TERN_AWUI_OMP_DIR` and `TERN_AWUI_NOTES_DIR` set them by hand. omp profiles (`OMP_PROFILE`) are not followed.
- Only main sessions bridge (`ctx.agent.kind === "main"`). Older extension versions also bridged subagents under the same pane, which took over the pane's status (idle while the main session still worked) and, on exit, unbridged it; the server now keeps every connection per pane and hands the pane back to the remaining one (`sync`).
