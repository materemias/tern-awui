# tern-awui: how it works

The reference behind the [README](../README.md): what each feature reads and writes, the omp extension's bridge protocol, installer steps, build, tests, configuration and the security model.

## Features in detail

Paths below use `<omp dir>` for omp's data folder (`~/.omp/agent` by default; `TERN_AWUI_OMP_DIR`), `<notes dir>` for Tern's notes (`~/.local/state/tern/notes` on Linux; `TERN_AWUI_NOTES_DIR`) and `<config dir>` for tern-mobile's own files (`~/.config/tern-mobile` on every OS; `TERN_AWUI_CONFIG`); [Configuration](#configuration) has the defaults per OS.

- **List**: every Tern block, grouped by the git root (or folder) of its cwd, newest activity first within and between groups. A row shows the status (working: pulsing green, blocked: red diamond and tinted row, idle: ring), the title's Nerd Font icon (served as a PUA-only subset of `SymbolsNerdFont-Regular.ttf`), the `TAG:` prefix and the time in that status. Only a busy row has a second line (`rowText` `status`, from the item's `activity`): while working, omp's working-row intent from the bridge's `run` (a changed intent rebuilds the list), while blocked on an `ask`, its question (read from the transcript once the status turns blocked; a tool approval has none, so the row stays one line). The rest is in the peek, a card under the row (above it in the lower part of the screen) that a 450 ms press (8 px of drift cancels it, and the tap that ends it doesn't open the row) or a 600 ms resting mouse opens, and a touch elsewhere, a scroll, Esc or the mouse leaving closes: omp's own recap for idle agents (the newest row of `session_recaps` in `<omp dir>/history.db`; italic, prefixed "Earlier:" when turns followed it), else the last prompt (scanned incrementally from the transcript), a file's folder or a shell's cwd, then project, branch and model. The rail puts the same text in its tooltip. An omp session is known through its bridge connection, which reports its session id and its status live: *blocked* while an `ask` dialog or a tool approval waits, else *working*/*idle*; an idle session's time counts from its last transcript entry. Blocks without a bridged omp (shells, other agents) are terminals.
- **Collapsing projects**: tapping a project header folds its sessions away (▸/▾); the folded set is kept per device in `localStorage` (`tern-mobile:collapsed-projects`). A folded header still shows "N active" for its working or blocked sessions, and a filter shows matches inside folded projects too.
- **Hiding old sessions**: **Hide old** in the dock hides sessions whose time in their status is over a day (the eye struck through, with the hidden count as a badge, while on; a toast confirms); kept per device in `localStorage` (`tern-mobile:hide-old`). Working, blocked, unseen and the open session always stay, as do blocks without a time (shells, notes), and a filter searches the hidden ones too.
- **List header and dock**: the header holds the status counts, a search button (phone only; the desktop sidebar always shows the filter field, and a typed filter keeps it open; Esc clears and closes it) and **+ omp**. With more than one Tern session the chips and a compact Waiting pill share one row under it; otherwise the Waiting strip sits there alone. The device switches (notifications, hide old, guide) float in a pill over the list's lower right corner (`.dock`, the list padded so its last rows clear it). Their visible state is the icon, their words stay as screen-reader labels and tooltips, and a tap shows a toast (`flash`) with the outcome; for notifications the toast waits until a tap's permission prompt and subscription settle.
- **Swiping between sessions** (`web/swipe.tsx`): a horizontal swipe on an open session moves to the neighbouring omp session in the list's order (`swipeOrder`), read when the gesture starts. That order skips shells and notes, old sessions while the list hides them, and folded projects, but always keeps the open block and the sessions the current run of swipes passed through, so swiping back reaches an old session opened from a notification. The screen follows the finger over the neighbour's title, with a "3 / 7" count over the header. A release past 30 % of the width, or a flick faster than 0.5 px/ms that is still moving at release, moves on. At the first or last session the screen gives only a fifth of the finger's travel and springs back. The move replaces the history entry and passes on where the old screen was entered from (`inheritOrigin`), so ‹ and system back still return to the list; ‹ during the slide-out cancels the move. Touches that start in a field, an overlay, a sideways scroller or within 24 px of the screen edge are left alone. A subagent chat swipes to the session's other subagents in the order its subagent list last showed them; opening one also asks `GET /api/blocks/<id>/subagents` for subagents started since, which join at the end. Alt+← and Alt+→ step through the same order from a keyboard, except in a text field, and switch at once, with no slide or preview, since a keyboard user has the list in view; where there is no neighbour they leave the browser's own shortcut alone.
- **Session wheel** (`web/swipe.tsx`): turning the finger up or down by more than 24 px during a sideways drag that is already over 80 px out opens a wheel of every session in the swipe order, highlighting the open session whichever way the drag went, with a 20 ms vibration where the browser has one. The screen moves 62 % aside, and the wheel fills the gap with each session's title, status and project, the highlighted one framed at mid-height and the open one marked with a rail. Every 48 px of vertical travel steps the highlight one row (with a shorter 8 ms vibration). A finger held within 64 px of the top or bottom keeps stepping, first after 220 ms and then faster down to every 60 ms, so sessions beyond the thumb's reach are still one gesture away. If the wheel opens with the finger already in one of those zones, that zone stays inert until the finger leaves it, so a sideways thumb swipe low on the screen doesn't step (and buzz) through the list by itself. Lifting opens the highlighted session as a swipe would; lifting on the open session, or dragging back within 40 px of the start, cancels. Subagent chats get the same wheel over their siblings.
- **Chat** (omp agents): the transcript tail from `<omp dir>/sessions/*/*_<id>.jsonl`, laid out like Tern's: prompts as a flat full-width band led by an accent `›`, assistant markdown full width, tool runs as one line (`▸ N tools · K failed  last intent`, tap to expand). Body text is a step below white (bold stays white). Each message hyphenates in its own language: `lang="hu"` when it contains ő/ű or more than 2 % accented vowels, else `lang="en"`. Tables are cards with row rules only, a small-caps header, faint zebra stripes and sideways scrolling; fenced code blocks are cards with their language in the corner. omp's figures render inline: ```` ```svg ```` blocks sanitized in place (with the `--fg`/`--accent`/`--c1`…`--c6` theme variables defined), ```` ```mermaid ```` blocks through mermaid (`securityLevel: strict`, dark theme), loaded as a separate chunk on first use; a diagram that fails to parse shows its source. Advisor notes (`custom_message` `advisor`) show as a card with each note's severity. A note with a `Key:` line shows the key, tap for its labeled lines (Evidence/Impact/Fix); the structure is an advisor-prompt convention, not omp's, so a note without `Key:` shows its own text as markdown, folded to two lines, whole after the tap. Meta lines (tool runs, turn rows, rules, cache misses, todo lists) use the body font at 12.5 px, muted; mono stays for code, tool names and terminals. On the desktop the chat, the composer, the session header and the extension notice keep a 720 px column (`--chat-width`); the lists keep 1100 px.
- **Turns** (`Turn` in `web/chat.tsx`): a turn is a prompt and everything up to the next one, in its own `<section class="chat-turn">` with a hairline above it. Its final reply is its last assistant text, or its last tool group when it said nothing. When an advisor note follows a reply directly (past the `turn` marker that reply ended with), the turn had already answered: that reply (the first such) stays in sight as the answer, each advisor note after it too, and the work those notes caused folds behind the same row, up to the final reply. A note that follows tool calls is mid-work and folds with them. `parseChat` reopens a turn on an advisor note that comes after its end (the agent answers it in the same turn), so the reply to the note ends it with a second `turn` marker, timed from the prompt and carrying the files that work changed; the work row takes the last marker, and runs while work follows it. Everything between the prompt and that reply (tool groups, interim text, todo lists, advisor and rule cards, cache misses, answered asks) folds behind one row under the prompt, `Worked 7m12s · 38 tools · 3 failed ›`, with the model and end time muted at its right; the `turn` entry gives the duration, else the time from the prompt to the turn's last entry. A tap unfolds the work in place; the state lives in the `Turn` component, keyed by the prompt's entry id, so it survives chat updates. The last turn without a `turn` entry counts as running (`Working · N tools`, unfolded) unless the `working` prop says the agent stopped, which a subagent's chat passes since a subagent's last turn ends with `yield` and never gets a `turn` entry. Nothing folds that the reader needs: open asks, recaps, and the chat's newest todo list while it has unfinished tasks (the working row's todo jump leads there). Entries before the first prompt render unfolded. The turn's changed files follow the reply. Prompts fold to six lines with a fade (`PromptText` in `web/parts.tsx`); the first tap shows the whole prompt. Once a prompt scrolls away above while its turn is still on screen, a one-line copy sticks to the top of the scroller (a zero-height `position: sticky` holder, shown by an `IntersectionObserver` on the prompt); a tap scrolls back to the prompt.
- **Injected rules**: omp's time-traveling stream rules (TTSR) that fired mid-turn show as Tern prints them, as faded lines without a card: `• inject: <name>` and the first line of the rule's body; tap for the whole body as markdown. Consecutive injections merge into one block. Names come from `ttsr_injection` rows (`injectedRules`). Bodies come from the `developer` message that follows the tool result (`<system-reminder reason="rule_violation" rule="<name>">`, omp's `ttsr-tool-reminder.md` and `ttsr-warning.md`): the tag line and the preamble line are dropped. Interrupting rules (`ttsr-interrupt.md`) are never written to the transcript, so they show by name only.
- **Session header and jump buttons** (`web/session.tsx`): the header holds ‹, the title (wrapping to two lines before it ellipsizes), ⋯ and × (Close, which asks first). On the wide layout (`useWide`) Park and Show on desktop are icon buttons beside × instead of the ⋯. ⋯ opens a small menu with **Park** (or **Unpark**) and **Show on desktop**, the pane actions that ask nothing; a tap outside or Escape closes it, ↑/↓ move between its rows. Once the reader scrolls more than 80 px up from the end, two round buttons sit stacked over the chat's lower right corner. ↑ (`jumpPrevPrompt`) glides to the prompt above the one at the top, or to the top before the first; repeated taps step on from the pending target. ↓ glides back to the end and follows new output again. A dot on it marks chat or streaming output that arrived while the reader was away; reaching the end clears it.
- **Cache misses**: like Tern's marker, a faded line with a database icon, `Cache miss · <N> tokens`, sits above an assistant message that rebuilt the prompt cache. The rule is omp's (`cache-invalidation-marker.ts`): the previous assistant message with usage read at least 2048 cached tokens, this one read none and wrote some, and its `cacheWrite + input` (the tokens shown) is at least 2048. Messages whose usage is all zero (aborted ones) leave the baseline alone. omp's reload of a transcript also hides misses right after a compaction, a model switch or a plan-mode toggle; the chat keeps them, as Tern does live, because they still resend the whole prompt.
- **Changed files** (`ChangedFile` in `lib/transcript.ts`, `web/changed-files.tsx`): a turn's `turn` entry carries `files`, the files its successful `edit`, `write` and `ast_edit` calls changed, merged by path in first-change order. Edit results give the paths (`details.path`, or `details.perFileResults` for a multi-file hashline edit) and omp's numbered diff, whose `+N|`/`-N|` lines are the counts. A `write` leaves both counts unknown (null): it may overwrite a whole file, so its content's length isn't the lines it changed. Without a path in the result the hashline `[PATH#TAG]` headers or `path` argument name the files, counts unknown. Paths are shown relative to the `cwd` of the transcript's `session` row when inside it, else as the agent wrote them; `local://` and other virtual paths are skipped. No git or file reads. The card shows `N changed files +A −R` (totals over files that report them) and a row per file; it starts collapsed above three files. Rows aren't links: the app has no viewer for arbitrary paths.
- **Prompt actions**: like omp in Tern, hovering a prompt (or tapping it on a phone) shows its time, **Copy** (the prompt text to the clipboard) and **Rewind**. Rewind, after a confirm and only while the session is idle, goes back to before that prompt and puts its text back in the composer: the server submits `/tern-mobile-rewind <entry id>`, a command the extension registers, because only command handlers may call `navigateTree`. The chat shows only the active path of the session tree, walked back by `parentId` from the leaf the bridge reports (a rewind moves it without writing the file), else from the file's last entry, so abandoned branches don't appear.
- **Block copy**: every code block and quote rendered by `<Markdown>` (replies, subagent prompts, side answers, opened Markdown files) gets a **Copy** button in its top right corner, added to the rendered DOM after each render. A code block sits in a `.code-card` so the button stays put while the code scrolls sideways; a quote's button floats right so text wraps around it. The label is CSS (`::after`), so a quote's `innerText`, which Copy puts on the clipboard, doesn't carry it. Mermaid and SVG figures get none.
- **Questions** (`lib/ask-form.ts`, `AskCard` in `web/chat.tsx`): from omp 18.18.3 on, `ask` takes one HTML form (`{ html }`). The card shows that form with the phone's own controls (radios, boxes, dropdowns, text fields, textareas, with their own `required`/`min`/`pattern` checks), sanitized by DOMPurify: scripts, styles and the form's own `<form>` go, buttons with everything inside them (omp skips those too), and every `id` and `name` gets a `user-content-` prefix, as do `for`, `list` and `aria-*` id references, so a field called `action` or `title` can't shadow a form or document property. Like omp's dialog, each radio or checkbox group of two or more options without an option starting "Other" gets a free-text *Other* field; its text replaces a radio group's pick, emptying it brings the form's own pick back, and picking a radio clears it. A form that is one radio group sends on a tap, the preselected option included; otherwise **Send answer** posts `{ id, values: { name: value or values }, other: { name: text } }`; a body without `values` is refused, so it can't submit the model's preselected values unseen. omp checks the form again on Submit, and some of its checks the browser doesn't make (`minlength` on an untouched prefilled value, a required field emptied on the desktop); when one fails, omp's dialog moves to the field in the Tern pane and writes no result. So a sent card that gets no result from the transcript within 10 s says omp hasn't taken the answer and unlocks, to fix it there or send again. omp keeps what the refused send typed, so the server remembers, per block, the values and Other texts it last typed into the open ask, and a resend toggles boxes and retypes text from those rather than from the form's starting values; it starts with the same reset keys, so the moved focus doesn't matter. The server parses the same HTML into the fields omp's dialog walks (a small tolerant parser that mirrors pi-tui's `html-form/parse.ts`: document order, radios and boxes grouped by type and name, hidden and button inputs skipped; the `entities` package decodes every HTML entity as a browser does, so a value like `caf&eacute;` matches what the phone posts) and replays the dialog's keyboard after checking that the ask is still open: Up, Shift+Tab once per field and once more to reach the first field whatever the desktop did, then per field Down or Up to a row and Space for radios and boxes, Left/Right for a dropdown, Ctrl+E and Ctrl+U (Ctrl+K too in a textarea) to empty a text field before its text is typed, Tab to the next field, and Tab, Enter on Submit. In omp ≥ 19 a desktop draft keeps the composer focused while the ask waits; Up from the composer's top line, or Shift+Tab (omp's "answer them" key there), hands the keys to the form and the draft stays. Before 19 Up ended the dialog's "typing edits your prompt" guard instead. Where Tab lands differs too: omp ≥ 19 puts the cursor on a group's first picked row (else its Other input when that holds text, else its first row), older omp on the first row, so rows are counted from the landing row that the form's values, or the last send's, give. The server picks the count by the omp release the extension reports (`omp` in its snapshot, read from `process.execPath`, which Tern runs as `…/omp/versions/<release>`). When the release is unknown (an extension from before this, omp run from a checkout), the server types only when both counts give the same keys, as in a form without preselected options, and otherwise refuses with a note to restart omp or answer in the pane, so a guess never submits a wrong pick. A radio or dropdown is set to the phone's pick outright; boxes are toggled and text retyped only where the answer differs from what the field holds, so a desktop edit to a field the phone left alone stays. In omp ≥ 19 a radio or box picked on the desktop before the phone answers moves the landing row, so the phone's count can end on the wrong row of that group. The answered card shows omp's `details.answers` as `question: answer` lines, each followed by the notes on its chosen options (`details.notes`, omp ≥ 18.18.8) as indented `Note on "option": text` lines. An ask written the old way (`questions[]`), which omp ≥ 19 accepts again, gets the form omp builds from it (`legacyAskHtml`: a fieldset per question, radios or boxes, the `recommended` option checked, a textarea for a question without options) and is marked `legacy`. omp 18.18.3 and later 18 releases refuse it, so an errored result turns it back into a failed tool call; an omp before 18.18.3 shows its own list dialog, so the server answers a legacy ask only on a known omp ≥ 19.
- **Question first**: an ask with one named field heads its card with that field's question (`ask-head`), as omp's dialog shows the question in its header above the form; the form's legend, heading or paragraph that says the same text is hidden (`ask-dup`), so it isn't said twice. Forms with several fields keep the form's own order.
- **Note images**: from omp 18.21.0 on, a note on an ask option can hold pasted images. omp appends them to the result's `content` after the text, renumbered across all notes so `[Image #N]` in `details.notes` names the Nth. `parseChat` keeps them as the ask entry's `images`, and the answered card turns each marker into a chip that opens its image, with the images as a numbered strip below, as a prompt's. The phone can't write notes itself.
- **Usage limits** (`lib/usage-limit.ts`, `LimitBar` in `web/session.tsx`): an idle session whose active path ends on an assistant message with `stopReason: "error"` (`lastStop` in `lib/transcript.ts`, walking back from the leaf over the last 512 KB, then the last 4 MB when that doesn't reach the leaf; a leaf neither reaches counts as unknown, not as moved on) gets a banner when its `errorMessage` reads as a limit. The read is shared while the file and leaf stay the same (`sharedRead`). `limitKind` sorts it into `wait` (`rate_limit_error`, `usage_limit_reached`, `turn_rate_limit_exceeded`, `Usage limit reached`, `Rate limit exceeded`, `FreeUsageLimitError`, Gemini's `exceeded your current quota` / `RESOURCE_EXHAUSTED`, a 429 naming a limit) or `spend` (a spend limit, `insufficient_quota`, insufficient or out of credits, a billing hard limit), and any other error gets none. The reset is `retry-after-ms=N` counted from the message's timestamp (or a `reset at` date with its zone) when that is in the future; else `omp usage --json --provider <message provider>` (argv, 10 s timeout, one run per provider per minute); else a zone-less `reset at YYYY-MM-DD HH:MM:SS`, read as local time since the provider's zone is unknown. In omp's report each account is blocked until the last of its exhausted limits resets (status `exhausted`, or `usedFraction` ≥ 1), and the session can go on once the first account frees, so the reset is the minimum over accounts. A `spend` limit has no reset. The server sends the open session a `limit` event (`{ kind, error, resetAt, continueAt }`, null for none) when the stream opens and whenever the pane's status, leaf or session changes; each look is numbered per pane, so a slow one (an `omp usage` run) never overwrites a newer one. The banner hides while a turn runs. `POST /api/blocks/<id>/continue` takes `{ when: "now", id }` (sends `Continue from where you stopped.` at once; `id` is the banner's, deduplicated like a prompt's), `{ when: "reset" }` (sets a continue for the reset plus a minute; 409 without a known reset) or `{ cancel: true }`; both need the session idle on a limit (409 otherwise) and an extension at protocol 6. The continue goes as the server's own message (`steer`: a bridge `send` with `keepDraft`), never through omp's editor, so a draft typed there stays. A continue is kept per pane with the session id, the errored entry's id and its own id, saved to `<config dir>/continues.json` (at most 100, the oldest dropped first), and timed with `setTimeout` in steps of at most 2³¹−1 ms. When it is due it goes only if the session is still idle on that same entry, rechecked after the transcript read; one look runs at a time per pane. Without its omp connected nothing is typed into the pane: the first report after a server restart looks again, and a timer drops it an hour after its time. A send that fails, or a transcript that doesn't tell, tries again every 30 s within that hour, and the banner says it is waiting for omp. A `submit` that reached the pane drops it (a deduplicated resend or a failed send doesn't), and so does a report showing the session moved on (another session, working or blocked, or a different last stop), a new connection for the pane, or omp disconnecting.
- **Tool approvals** (`ApprovalCard` in `web/session.tsx`, `approvalView` in `server.ts`): the extension (protocol 5) reports omp's `tool_approval_requested` as `approval: { id, tool, reason }` in its snapshot, the first one asked while several wait, and drops it on `tool_approval_resolved`. The server reads that call's arguments from the transcript (`pendingCall` in `lib/transcript.ts`: omp writes the assistant message before it asks) and sends phones an `approval` event, null once nothing waits. Arguments go whole, never cut, so nothing the call does is hidden; when the transcript's tail doesn't hold the call, `args` is null, the card says so and **Approve once** is disabled (the server refuses it too), leaving Deny. An older extension reports no approvals; for a blocked session without an open `ask`, the newest call without a result stands in, with no reason. The card shows the tool, omp's reason and each argument (`i` left out): an `edit` patch reads as its file, each step in words (`readPatch` in `web/lib.ts`: `PUT >94:` is "Insert after line 94") and the lines it writes; `command`, `code`, `content`, `input`, `html` and long or multi-line values as scrolling blocks; the rest inline. **Approve once** and **Deny** post `/api/blocks/<id>/approve` with the call's id; the server rechecks that the pane still asks about that call, then sends omp's approve key `ctrl+q` (it approves wherever the dialog's cursor sits, even with a draft in the editor) or `Escape`. The row's second line and the notification say `Allow edit? Restricted folder: …`.
- **Deny with a reason**: omp's approval dialog has no reason field, so the card's **Deny with a reason…** opens a text box (up to 4000 characters, `MAX_DENY_REASON` in `lib/bridge-state.ts`) and **Deny** posts it as `reason` (`denyReason` checks it, for the server and the demo). The server takes a reason only with `allow: false`, and only from an omp bridged at protocol 6 (409 before any key otherwise). It presses Escape as for a plain Deny, then sends the reason as the server's own message (`steer`: a bridge `send` with `keepDraft`). omp takes it as a steer of the running turn and leaves its editor alone: no key lands in a dialog that opened next and a desktop draft stays. omp also denies a call that waits when a steer arrives, so a second approval already queued is denied with the same reason rather than approved. If Escape fails, nothing else is sent and a retry can answer the call. If the deny lands but the reason doesn't, the reply is a 502 with `denied: true`. The call is answered by then and a retry would be refused, so the phone keeps the error and the reason above the composer until it is dismissed, and the reason can go as a message. The 5-second duplicate guard covers the reason too: a second tap sends neither the key nor the reason.
- **Answered line** (`answered` in `Session`, `AnsweredContext` in `web/chat.tsx`): once omp takes an answer the phone sent, a muted line above the composer says so: `✓ Approved: bash`, `✕ Denied: edit` (with `· reason sent` when a reason went too) or `✓ Answered: <question>`. An approval counts as taken when both its POST succeeded and the `approval` event dropped that call, in either order (a deny with a reason closes the dialog before its reply); a failed POST, or a dialog still open after 10 s, confirms nothing, and another call's dialog never confirms it. An ask counts once the transcript holds its result. The line fades out over 4 seconds (with reduced motion it disappears without fading). It belongs to the block and the omp session it was answered in, so it never follows you to another session.
- **Images**: a prompt's pasted images follow its text as 64 px squares cropped from the top left, in one row that scrolls sideways, numbered when there are several (`Thumbs` with `strip`); outside the six-line fold, so they show while the text is folded. omp's `[Image #N, WxH]` in the text becomes a chip opening image N (`withImageChips`; a name with no such image stays text), and the pinned prompt line writes it `[image N]`. Images that tools read (screenshots) show whole under the tool line, at their own aspect ratio (at most 180 px high and 480 px wide, never upscaled); a folded turn's work row shows the first of them small, with `+N` for the rest. A tap opens them full screen. The full-screen view pages through every image of the turn (the prompt's and the screenshots up to the next prompt) in a scroll-snapping strip: swipe on touch screens, ‹ › and the arrow keys where there's a pointer that hovers. It pushes a history entry holding the image's src, so back closes it without leaving the session and forward reopens it; a tap or Escape closes it and pops that entry, and so does the image leaving the transcript (a rewind). The transcript stores most as `blob:sha256:<hash>`, served by `/api/blob/<hash>?type=<mime>` from `<omp dir>/blobs/<hash>` (PNG/JPEG/WebP/GIF only); small ones sit inline and go to the page as `data:` URLs.
- **Assistant screenshots and document images**: Markdown images pointing to absolute local PNG/JPEG/WebP/GIF files, or in a reply to `local://<name>` (resolved inside the session's `local://` folder, `<transcript without .jsonl>/local/`, which its subagents share; anything escaping it is ignored), are served through the authenticated blob API without changing the transcript. Opened Markdown files get the same, and also resolve relative paths against the file's folder; there both kinds are percent-decoded with `?query`/`#fragment` dropped. Assistant replies take absolute paths as written and never resolve relative ones. Each file is limited to 16 MiB; the server keeps up to 64 MiB or 128 images in memory and up to 4,096 authorized source paths. Evicted image bytes can be reloaded only from an unchanged, previously indexed file with the same content hash. Missing files, unsupported formats and final-file symlinks are not imported. A document's images are resolved when the document changes, not when only an image does.
- **Images in prompts**: pasting an image into the composer, or picking one with the attach button (`<input type="file" accept="image/*" multiple>`, which on a phone offers camera, photos and files; non-image picks are skipped), shows it as a preview with a × above the text, up to 8 (omp sessions only). On touch screens with `navigator.clipboard.read`, where Android's text menu offers Paste only for text, the attach button opens a two-row menu above itself instead: **Photo or file** (the picker) and **Paste from clipboard**, which reads the clipboard with `navigator.clipboard.read()` (one image per clipboard item; Chrome asks for the permission once) into the same tray; a transparent scrim closes the menu on any other tap. Elsewhere the button opens the picker directly. PNG/JPEG/WebP/GIF under 3 MB go as they are; anything bigger or of another type is scaled to a 2048 px long edge and sent as JPEG. On send, the text and images reach omp as one user message through the bridge (`send` → `pi.sendUserMessage`: a new turn when idle, a steer while working), and the desktop draft is cleared. Shells and sessions without the bridge refuse images and show no attach button.
- **Screen**: omp agents: `tern capture --surfaces`, the last 160 lines of the main region (transcript text and progress; not overlay dialogs), reached through **Raw** at the start of the key bar (⌨); the button then reads **Chat** and switches back. Plain terminals: `tern capture --html`, one screen with colors, sanitized to `<pre>`/`<span style>`, polled every 450 ms; prompt glyphs come from the bundled symbols font. In terminals the composer types live onto the shell's own line (each edit becomes Backspaces plus new text, autocorrect off), the soft keyboard's Enter presses Enter, and the key bar is open by default, so interactive tools like `op`/fzf work: type to filter, ↑/↓, ⏎. Tab completion changes the line behind the composer; any key-bar key clears the composer.
- **Notes and files**: file blocks (`file` in `tern ls --json`) open read-only. - **Voice calls**: the microphone button (bridged omp sessions whose extension reports the `voice` cap, i.e. omp has `ctx.startLive`, interactive mode only) runs omp's `/live` with the phone as microphone and speaker. The page opens the microphone (`getUserMedia` with echo cancellation, noise suppression and auto gain), makes an `RTCPeerConnection` with that track and an `oai-events` data channel, waits up to 1.5 s for its ICE candidates and posts the offer with a fresh attempt id to `/api/blocks/<id>/voice`. The server records the call at once (phase `connecting`, tagged with the attempt) and relays the offer to the extension (`voice`, 30 s timeout), which calls `ctx.startLive({ sdpOffer })`; omp signals the call to OpenAI with its Codex sign-in, opens the call's control socket and answers. The answer goes back to the page, and from then on audio flows between the phone and OpenAI, not through the server. omp keeps everything else: its live prompt, delegations into the session as ordinary turns, and its TUI visualizer (whose stop key or `/live` also ends the call). The extension forwards the call's phase, its transcript lines (streaming lines at most every 150 ms, final lines at once) and one `end` as `voice` messages; the server folds them into one call state per pane (`foldVoice` in `lib/bridge-state.ts`) and streams it as `voice` events (null when there is none, also on stream open). The bar above the composer shows the phase, the last line each side said, mute and hang-up; a phone watching a call another device runs sees it with hang-up only, and its microphone button is disabled. Mute silences the phone's track locally; omp's `muted` phase (its mute key) silences it too, as omp has no host track to mute. One call per session: the server refuses a second from the moment the first is posted, the extension refuses one too, and omp refuses while a desktop `/live` runs. The phone acts only on reports tagged with its own attempt, and once it has seen one, a later "no call" (its stream reconnected after missing the end) ends its side as well. Automatic hang-ups carry the attempt (`/api/blocks/<id>/hangup` with `{ attempt }`), and the extension then stops only that start's call, so a phone whose start lost, failed or timed out can't end another phone's call; hanging up another device's call sends no attempt. A refused offer (4xx) sends no hang-up; a failed or timed-out start does, and on a timeout the server sends it too, since omp may still bring the call up. A call ends on hang-up, on leaving the session screen or the page (`pagehide`, a keepalive POST), when the peer's connection fails, on a new omp session, when another omp takes over the pane, when the bridge socket closes (the extension hangs up; the server tells the phones "omp disconnected"), and 30 s after it is left with no phone watching the pane (also when the phone left before the call came up). The extension forgets a call once omp's stop settles, even if omp never reports its end. Hanging up or leaving while the microphone permission prompt is open, or while the peer gathers candidates, cancels the start: a late grant's tracks are stopped and no offer goes out. From the tap until the call ends the page holds a Screen Wake Lock (`useWakeLock`), so the screen stays on; browsers drop it whenever the page hides, so it is requested again when the page is visible, and browsers without the API or refusing it (battery saver) keep their usual screen timeout. While a call runs the page also keeps its stream open when hidden, and reconnects it if it fails, so it still gets the phase if the screen turns off anyway.

- **Extension check**: the app tells you when omp's extension isn't the one this checkout ships, and how to fix it. - **Desktop browser**: at 1000 px and wider the list stays in a 360 px left sidebar (the open session highlighted). The session uses the remaining space with a centered content column up to 1100 px wide, shared by its transcript, header, composer and extension notice. Narrower windows retain the existing gutters; mobile layout is unchanged. All of it lives behind one `@media (min-width: 1000px)` block and the `useWide()` switch in `App`. The back-to-exit guard and the session's ‹ are phone-only; subagent screens keep their ‹, which leads back to the session.
- **Sidebar rail**: the "tern" brand in the list header is the minimize button: on hover or keyboard focus `«` replaces the word in the same grid cell, so the header doesn't shift. It or Ctrl+\ (⌘\; Ctrl+B is Firefox's bookmarks sidebar) minimizes the sidebar to a 56 px rail, `»` or the shortcut expands it; `App` keeps the choice in `localStorage` (`tern-mobile:sidebar-rail`) and `Home` renders the rail when `rail` is set. One round button per session links to it, showing the title's Nerd Font icon, else the block's tag (first 3 letters), else two letters of the title (`railGlyph`; omp's π alone would make sessions look the same). The ring takes the status colour, the unseen dot sits on its corner, the open session gets an accent bar, and the tooltip is the title and the row's subline. Project labels (first 4 letters) toggle the same collapsed set as the full list and show the active count when shut. The header keeps the connection dot, the blocked count and the bell, the foot the new-omp `+`. The rail ignores the filter typed in the full list; hiding old sessions still applies. The list header's counts are the rows' status dot (smaller, without the pulse) and a number each, with "N blocked/working/idle" as their tooltip and accessible name.

Updates arrive over one SSE stream per screen, pushed rather than polled. The server follows `tern events` (any event except the `client_*` pair every CLI call logs), bridge changes (connect, disconnect, status, model, thinking, tier, session id, protocol, build, caps) and new or removed recaps in `<omp dir>/history.db` (its other writes, such as prompt history, are ignored: a write is checked against the recap count and newest id, which assumes omp only inserts recaps); each batch (150 ms) rebuilds the list once, worked out once into a comparison key, and every open stream rechecks it. A stream sends the whole list once (`state`); after that a change goes as a `patch`: everything but the rows, the order of every row by project, and only the rows that changed (`lib/state-patch.ts`). A page that can't apply a patch (it lacks a row) reconnects for a full copy. Only Tern's own events, a close, a new tab, an omp leaving the bridge and the 15 s recheck rerun `tern ls --json`; a rebuild for another bridge change reuses the cached block tree. The context gauge is not part of the list: it goes as a `context` event to the phones on that pane (sent on open, on a new session, whenever omp's estimate moves, every 2 s while it works, and when the compaction settings change), with `compactAt` worked out from omp config. The open transcript or file is followed with a watch on its folder. Only terminal screens are still polled (Tern has no output event): every 450 ms for shells, 1.2 s for an omp's Raw screen, and only while one is open. Streams showing the same thing share the work: polls land on those slot boundaries so all phones on a block share one `tern capture` per slot, and one transcript parse per session and file stamp is shared (the newest 32 kept), with local images attached per delivery so an image overwritten in place gets its new hash. A 15 s recheck backs up missed events. Caches follow what is open: transcript facts, paths and subagent scans of sessions no longer bridged, git answers for folders no open block uses, and header cwds of deleted transcripts are dropped. Clocks on the page (row ages, the working row's timer) stop while the page is hidden.

An open chat works the same way. After the first full `chat`, a stream sends `chatpatch`: the previous copy's length (`base`), the run of its entries the new window still starts with (`drop`, `keep`), the entries after that run (`add`), and any other top-level fields. Entries are compared by their serialized JSON, per stream; the transcript parse stays shared across phones. An unchanged chat sends nothing, and when the patch would not be smaller (a rewind that rewrote the window) the full `chat` goes instead. Appending one entry to an 80-entry chat costs about 100 B to 3.5 KB instead of the 12 to 25 KB full copy. A page that can't apply a patch (no chat yet, or another `base`) reconnects for a full copy, as for a list `patch`. A new stream still starts with a full `chat`. Shared code: `lib/chat-patch.ts`.

The app holds a stream only while it is visible: 10 s after it is hidden (another app, screen off, a background tab) the stream closes and nothing flows; it reopens when the app comes back. With no phone watching, sessions also send no live text and count as unseen again. Closed or hidden, only Web Push notifications reach the phone.

- **Live text**: while a phone has a session open, the extension forwards the assistant message omp is writing (`message_update`, text parts only, at most every 200 ms) and the phone shows it below the transcript as it grows. When the message ends, the copy stays until the transcript write brings the final one, so nothing flickers. Sessions nobody watches send nothing (the server tells each omp with `watch` on/off).
- **Queued steers and follow-ups**: prompts sent while the agent works show below the transcript until omp takes them: `↳` for a steer, `→` for a follow-up held until the turn ends. The web composer's `→` button, Ctrl+Enter or Ctrl+Q sends an explicit follow-up through `pi.sendUserMessage(…, { deliverAs: "followUp" })`. For interactive desktop input beginning exactly with omp's `->` or `=>` queue syntax, the extension removes that prefix from the displayed text and reports a follow-up; leading whitespace, embedded arrows and RPC text are not interpreted as queue syntax. This changes only the display, not the input event or delivery. Numbered batches remain one locally tracked group. Extensions cannot read omp's actual queue, so tracked prompts clear when `ctx.hasPendingMessages()` becomes false. Desktop Ctrl+Q without a prefix still appears as `↳`, because the input event does not expose the submitting key. Queue updates travel in bridge state and `queued` SSE events.
- **Tool intents**: a tool line shows the call's `i`; eval calls show their `title`; with neither, the first line of `command`/`path`/…/`code`.
- **Tool facts** (`lib/tool-facts.ts`): after the intent, a tool line may show what the call's output says, such as `412 passed · 3 failed: orders > refunds a cancelled order`, `no type errors` or `4 results in 2 files`; the folded group's line ends with its last call's facts. Facts that don't fit beside the intent take their own line, cut with an ellipsis. The server reads them from the tool result in `parseChat`, only for the calls in the entries it sends, and sends only the short line (`facts`, at most 160 characters), never the output. A parser answers only for an output shape it is sure of, after dropping escape codes and omp's notes (`Wall time`, `Command exited with code`); an output no parser recognises gets nothing. For bash, it reads the summaries of bun test (` 24 pass`/` 1 fail`, kept when a tail cut the pass line or a grep the lines after it), vitest (`Test Files` then `Tests`), jest (`Tests:`), pytest (`1 failed, 214 passed in 19.61s`), cargo test (`test result:`, summed over binaries) and go test (`ok`/`FAIL` per package), and names the first failing test where the runner prints one; cargo's and go's sums are a lower bound (`4+ passed`) when omp cut the output. tsc facts need a command that runs tsc (or a typecheck script). Counts come from pretty mode's `Found N errors in M files.`, else from its error lines, as `N+` when a pipe or omp's truncation may have hidden some (a `tail` that kept the `$ tsc` echo of `bun run`/npm still shows them all). `no type errors` needs that echo with nothing cut, no runner failure line (`error: script`, `npm error`, `ERR_PNPM_`, `tsc: not found`) and, for a single command, a call that didn't fail; or a lone `tsc` command that succeeded silently. eslint's `✖ N problems (E errors, W warnings)`, a single git stat line (` 3 files changed, 12 insertions(+), 4 deletions(-)`; two in one output are ambiguous) and git status (long form with one `On branch` header, or short form when every line is a status line and the segment has no redirect, pipe or command substitution, so empty output means clean) complete the list. Several facts in one output join in output order. A command sent to the background or cut short by omp proves nothing by its silence. omp's grep tool already counts its matches in `details` (`matchCount`, `fileCount`); a reached limit (`perFileLimitReached`, `fileLimitReached`…) turns the count into `10+`. When omp later prunes an old result (`[shaken …]`), its call loses the facts.
- **Working row**: while a session works, the bottom of the chat shows omp's own working row: a braille spinner, the turn's running time (`31.6s` in tenths for the first minute, then `3m 05s` each second) and what the turn is doing, in mono with an accent highlight sweeping over it (no animation under `prefers-reduced-motion`). The extension reports `run`: `since` from omp's `agent_start`, and `intent`, the `i` argument of the tool call omp is streaming (`message_update`), then the label omp resolves when it runs (`tool_execution_start`'s `intent`, which falls back to the tool's own, like eval's "running javascript"); "" shows as "Working…". It is null while idle and after `agent_end`. The server sends it only to the open session's stream (`run`, also on open), and clears it when the pane's bridge is replaced or lost. Without it (older extensions) the row counts from the status change. While the newest todo list in the chat has an unfinished task, the row ends in a chip with its progress and task: `2/5 · ` done of all tasks across phases, then the task in progress, else the next pending one, else a blocked one. The chip takes up to 55 % of the row and the intent keeps the rest, both cut with an ellipsis, so the row stays one line on a phone. A tap on it glides the chat to that list (`.todo[data-newest]`), opening it if a tap had folded it.
- **Todo lists**: a tool line that ran `todo` carries omp's list as that call left it (`details.phases` of the tool result; the newest per tool group). The newest list in the chat shows every task, in the body font: per-phase headings when there are several, `✓` done (faded), `▸` in progress, `○` pending, `!` blocked with its reason. Older ones collapse to one line (`done/total`, blocked count, the current task); a tap toggles either. A folded turn keeps the newest list in sight while it has unfinished tasks.
- **Subagents and background jobs**: the extension samples `ctx.getAsyncJobSnapshot()` once a second and reports the running jobs (id, type, label, agent name, start). A row with jobs gets a line like "2 subagents · 1 background job"; the session shows each one under the transcript (`⑂` subagent, `⧗` other job) with its name and run time. Running `task`/`eval` subagents keep the session *working* even while its own turn has yielded to wait for them, so the list and "finished" notifications don't treat it as done; a backgrounded bash job (a watcher, a server) doesn't.
- **Subagent transcripts** (read-only): omp writes each subagent's transcript next to the session's, in the folder named like the session's file without `.jsonl` (`<stamp>_<id>/<AgentName>.jsonl`; the job's agent name is the basename). Tapping a running subagent in the `⑂` strip opens its chat (`#/b/<block>/sub/<name>`); whenever the session has subagents, **Subagents (N)** under the transcript lists all of them, finished ones too (`#/b/<block>/sub`): running first, then newest activity, each with its result (else its last reply, else its last tool intent), message count and age. It stays once every subagent has finished. A subagent's chat is the session's chat renderer (tools, todo lists, images, markdown) without composer, prompt actions or answerable questions, under a header with its name, running/finished and the parent session; its prompts, written by the parent agent, render as Markdown with every stretch drawn open; the text it hands back with `yield` (`data.result`) shows as its final reply. It updates as the file grows (`/api/stream?block=<id>&view=chat&sub=<name>`; the list: `view=subagents` or `GET /api/blocks/<id>/subagents`). Names must be plain (`[A-Za-z0-9][\w.-]*`, so no paths, dot files or `__advisor.<model>.jsonl` advisor transcripts; anything else is a 400), symlinks are ignored, and `.md` results and `.log` tool output aren't subagents. Subagents show only while the session's omp is bridged (its session id finds the folder).
- **Table charts**: like omp in the terminal, a markdown table with numbers gets a bar chart under it (`web/charts.ts`): one panel per measure, one colored bar per option, each panel scaled on its own. Cells are read as number, range (`0.23–1.04 MB`, plotted at its middle) and unit (bytes, time, %, `$`, counts; a trailing parenthetical is ignored). Rows are the measures when each row keeps one unit and the columns mix them, else the columns are. The best value is marked only when the measure's name points one way (time, size, cost, errors… lower; accuracy, reusable, throughput, revenue… higher; "error rate"-style names that match both, and names that match neither, get no best). The headline is the "X is best on …" sweep when one option wins at least two measures; omp's model-picked headlines are not reproduced.
- **Stretchtext replies**: for omp sessions running the `stretch.ts` extension ([pro-vi/cc-stretch](https://github.com/pro-vi/cc-stretch) for omp; not part of tern-awui), where the model writes `{{short|long}}`. A reply shows each short form as a dotted-underline link (`#stretch/open/<i>`, never routed); a tap grows the long form in place over up to 700 ms and puts a `«` after it, which closes it and everything nested in it. Live text shows short forms only; btw answers show every long form. The transcript gives such a reply part its block id, `<message timestamp>.<content index>` as stretch.ts names it. When the pane's omp runs stretch.ts, the open state is shared both ways: the extension reports stretch.ts's open keys per block in its snapshot (`stretch`, through `globalThis[Symbol.for("omp-stretch")].bridge`, version 1), the server streams changes as `stretch` events, and a tap posts `/api/blocks/<id>/stretch`, which the extension applies with the bridge's `setOpen`, so the pane grows it too and the next prompt's read note counts it. `/stretch off` in omp (`off: true`) draws every long form. Without stretch.ts (or in a subagent's chat) open stretches are local to the page.
- **Stretchtext parser copy**: `web/stretch-core.ts` is an unchanged copy of `stretch-core.ts` from [omp-stretch](https://github.com/materemias/omp-stretch), deepen action (✦) included; tern-awui needs no omp-stretch package to show stretches. ✦ needs an omp-stretch with deepen in the pane and the current tern-mobile extension; older versions of either still open and close stretches. Phone and pane sync only while both name stretches alike, which the key tests in `web/stretch.test.ts` pin. After a parser change in omp-stretch, copy the file over again.
- **Recaps in the chat**: omp writes an idle recap to `history.db` (`session_recaps`) once the terminal has sat idle for `recap.idleSeconds`, and prints it under the turn with `※`. The chat shows every recap of the session the same way: `readChat` reads them all (`querySessionRecaps`) and `withRecaps` merges them by time, so each lands after the last entry before it was written (its whole-second `created_at` counts as the end of that second) and before the next prompt. Recaps older than the chat's first shown entry are dropped with the part of the transcript left out. A recap arrives without a transcript write, so the chat stream's etag includes the session's newest recap, which the history.db watcher already refreshes. A recap of a branch rewound away still shows at its time, before the prompt that followed the rewind.

## Draft mirroring (omp extension)

`omp-extension/tern-mobile.ts`, symlinked to `~/.omp/agent/extensions/tern-mobile.ts`, runs in every omp started in a Tern pane (`$TERN_PANE`). The installer writes `~/.config/tern-mobile/bridge.json` with the local WebSocket endpoint and absolute bridge-token path, so omp started independently finds custom ports and config directories. Without valid discovery settings it uses `ws://127.0.0.1:4380/bridge` and the default config folder. Explicit `$TERN_AWUI_BRIDGE` and `$TERN_AWUI_TOKEN_FILE` override discovery; `$TERN_AWUI_CONFIG` overrides the discovered token directory. Restart existing omp sessions after changing these settings. The extension:

- polls `ctx.ui.getEditorText()` every 100 ms and sends the draft, model, thinking level and idle state when they change;
- applies `set` (phone keystrokes → `setEditorText`), `model` (`provider/id[:thinking]` → `pi.setModel` + `setThinkingLevel`), `thinking`, `tier` (`pi.setServiceTier`), and answers `models` with the catalog;
- reports the current model's thinking `levels`, `tiers` and active `tier`;
- while watched, sends the message being written (`live`) and its end;
- reports the running turn (`run`: its start and the current tool call's intent, null when idle);
- reports the prompts waiting in omp's queue (`queued`) and the session's leaf entry (`leaf`, `-` for none);
- reports stretch.ts's open stretches (`stretch`, null without it) and applies `stretch` (open or close one in the pane);
- reports its bridge `protocol` and `build` (the sha256 prefix of its own file), so the app can flag a session that loaded another version (see *Extension check*);
- starts a voice call with the phone's offer (`voice` → `ctx.startLive`), ends it on `hangup`, and reports its phase, transcript lines and end (`voice`; see *Voice calls*);
- registers `/tern-mobile-rewind`, which the phone's Rewind submits.

The phone shows a green dot by the model chip while mirroring. Its own edits win for 800 ms over echoes from the desktop; live keystrokes are last-writer-wins on both sides. A draft write may carry the draft it replaces (`expected`, used by the phone's clear after a handled command); the extension refuses it ("draft changed") when omp's editor holds something else by then. Keystrokes don't carry it: the server's copy lags omp's editor by up to one 100 ms poll, so a guard would refuse the phone's own fast typing. Submitting always sets the draft to the phone's text, waits for omp's acknowledgment, then sends Enter, so slash commands work as typed. An image or follow-up `send` clears omp's editor only when it still holds the draft the server last saw. A `send` with `keepDraft` (protocol 6: a deny's reason, a usage-limit continue) doesn't touch the editor at all.

Every prompt `submit` carries the phone's id for the prompt (`id`, a UUID). The server refuses anything but 1 to 64 letters, digits and dashes with 400. After a failed send, resending the same text and images reuses the id; any change, or a success, starts a new one. The phone keeps one such id for steers and one for follow-ups, so a steer sent in between leaves a failed follow-up's id for its retry. A resend whose id is still running is not sent again: the server waits for that request's outcome. The server remembers the ids of sends that succeeded, per block, for 10 minutes (at most 500, oldest dropped) and answers a repeat with success without typing anything; a failed send is forgotten, so its retry runs. For image and follow-up sends the extension also remembers the last 100 ids it handed to omp, for 10 minutes. So a send whose reply was lost (omp answering after the 2 s deadline, or the phone switching networks) runs once. An extension from before ignores the id.

omp loads extensions at startup: sessions started before the extension was installed don't mirror until restarted, and sessions started before it changed keep the version they loaded (the app flags them). Without the bridge, the composer types the prompt with `tern send` and the model sheet can only cycle (Ctrl+P).

Tern's CLI can't read a pane's editor (`tern capture` returns only the main surface region), and the plugin API's `surface()` returns nothing for hidden panes, so the draft is read from omp.

## Sharing to the app

The manifest declares a share target: Android's share sheet lists the installed app and posts the title, text, link and images (`images`, any `image/*`) as `multipart/form-data` to `/share`. `sw.js` answers that post itself: it stores the form as a response in the `tern-share` cache under `/share/<id>` (dropping any older share nobody picked) and redirects to `/?share=<id>`. On load, `web/share.ts` reads and deletes that entry, sets the address back to `#/` and holds the share. The list then shows a sheet of every open omp session (only those bridged to tern-mobile when the share has images, which need the bridge); one tap opens the session, and its composer adds the text (title, text and link, each once) after its draft, with a blank line between. The composer waits for the session's first draft report for that, so a desktop draft is kept. The images go through the same path as a pasted image, with the same 8-image limit and resizing. Nothing is sent. Cancel or a tap outside drops it; a picked share whose composer never opened is dropped after 2 minutes or when another share is picked. A share posted before the service worker controls the page reaches the server, which redirects it to `/`; the share is lost. Starting a new omp with the share isn't offered.

The manifest's one shortcut, **Waiting** (long-press the app icon), opens `/#/waiting`.

The demo has no manifest or service worker; `?share=demo` opens the picker with a sample text and image.

## Notifications

**Notifications** in the dock (the bell in the rail's header) turns on Web Push for that device (service worker `sw.js`, VAPID keys in `~/.config/tern-mobile/vapid.json`, subscriptions in `push.json`, both mode 600). It has four looks: slashed (off, or blocked in site settings), slashed in red (stopped: Android took notifications away from the installed app, see below), dimmed and pulsing (pending: asking for permission, subscribing, or waiting for the server to store the subscription; taps are ignored), and a green dot (on: the server confirmed it). The choice is kept per device in `localStorage` (`tern-mobile:push`); on every load a device that chose *on* checks its subscription, silently makes a new one if the browser dropped it or it belongs to another VAPID key, and re-sends it to the server, so updates and reloads don't turn notifications off. Bridged omp sessions trigger them:

- **Needs you**: the status turns *blocked* (an `ask` or a tool approval); the body is the question.
- **Finished**: *working* → *idle* that stays idle for 3 s; the body is the start of the last reply.
- **On you** (Waiting): a session or plain pane gains a wait with ball `on_me`, compared by row and wait id against the previous view, so a second wait firing notifies again and one that leaves and returns does too. The first view after the server starts only sets the baseline. A row in a pane becomes unseen as *blocked* and uses that pane's tag, so it clears like any other. A wait flagged only because the agent asks a question (the CLI's reason `agent asks a question`) pushes nothing while the session is *blocked*, since its status announced that ask; any other wait firing on that session still does. A closed session has no pane: its notification is tagged `w<session>`, opens `#/waiting`, and the Waiting popup closes those it shows.

One notification per session (a newer one replaces it); tapping opens that session. A fresh bridge connection (restarted omp) never notifies. Payloads are end-to-end encrypted, but they travel through the browser's push service (FCM for Chrome), which also sees the VAPID subject: `mailto:` the first allowed login when it is an address, else a placeholder (`TERN_AWUI_VAPID_SUBJECT` overrides). Subscriptions the push service reports as gone (404/410) are dropped. The service log names each removal: `push: … reported a subscription gone`, or `push: a device on … removed a subscription` when a device unsubscribes one it had registered (turning notifications off, or the service worker retiring a subscription the browser replaced).

While visible and connected, the page discovers session notifications tagged `b<block>`, then fetches `/api/state` with a timeout before closing any whose update is no longer unseen. Fetching after discovery prevents a newly displayed unread notification from being dismissed using older SSE state, even before the worker's display message arrives. Opening a session, starting another turn on either device, or closing the pane clears its update. After displaying a notification, the service worker messages open pages to reconnect their SSE streams for a fresh snapshot and trigger cleanup. Hidden or disconnected pages wait for fresh state before dismissing anything. No silent push is sent to clear notifications while the app is closed or suspended; they are reconciled when it resumes.

If the unread badge count differs from the number of unseen rows in either snapshot, dismissal waits. A failed or malformed Tern pane listing can omit rows while retaining unread updates; it must not be treated as proof that those sessions closed.

A device that chose *on* repeats the load-time check whenever the app returns to the foreground or the network comes back, because an installed app can stay open in the background for days while the server prunes or loses its subscription. A failed recheck keeps the bell on and tries again next time. A failed first check (the server restarting during an update, say) retries on its own after 5 s, doubling up to once a minute, until the server takes the subscription; a retry that comes due while a tap on the bell is still working waits for it. If the browser forgot the notification permission (it reads *default* again), the device can't ask without a tap, so the first tap anywhere in the app asks once more and subscribes when granted, except in the stopped state below, where only the bell asks. A dismissed prompt is not asked again on later taps until the permission has been granted and lost again. A toggle made during a recheck wins. Turning on also asks the browser to keep the origin's storage (`navigator.storage.persist()`), which holds the choice and the subscription; the browser may refuse, and the app goes on without it. When the browser replaces a subscription on its own (`pushsubscriptionchange`), the service worker registers the new one, so this works with the app closed.

On Android, an app installed from Chrome is its own Android app (a WebAPK) with its own notification permission. Without that permission, Chrome resets the site's permission to *default* and drops the push subscription each time the app opens from its icon, and `Notification.requestPermission()` shows nothing and never settles: Chrome hands the prompt to another installed app of the same host (seen with Chrome 155 on Android 16). The bell therefore stops waiting after 10 s and counts the request as *default*, leaving a stopped bell stopped. An answer that still comes later counts: a grant with no newer tap on the bell records the choice and subscribes. A permission request answered *denied*, or a tap on a blocked bell, shows where to allow notifications: App info → Notifications for the installed app, the site's permissions in a browser tab. A request answered *default* (a dismissed prompt) shows nothing, except in the installed Android app, where Android blocking the prompt looks the same, so the message mentions App info. The page can't open those screens itself: Chrome follows `intent:` links only to activities marked browsable, and Android's settings screens aren't.

No web API shows that Android permission: `Notification.permission`, `permissions.query` and `pushManager.permissionState` can all read *granted* while it is off, because a request from the bell may be answered with the permission of another installed app of the same host. Notifications then work until the next launch from the icon. The app goes by what that launch leaves behind instead: in the installed Android app, a device that chose *on* that finds the permission back at *default* and no subscription shows the bell **stopped** (slashed, red, "Notifications stopped: Android blocks this app") and remembers it (`tern-mobile:push-app-blocked` in `localStorage`). In that state a tap anywhere doesn't ask again (the request would hang or borrow again), only the bell does, and a grant from it turns notifications on with a warning that they'll stop at the next launch unless App info allows them. Only turning notifications off clears the mark: no page load proves the Android permission came back, since a page opened from a notification or running on a borrowed grant looks like a healthy launch. The stopped look itself is decided afresh at every check.

## Requirements

On every OS: [Bun](https://bun.sh) (1.4 tested), Tern with its `tern` CLI on `PATH` and omp (`omp` on `PATH`). The installer also needs Tailscale logged in with MagicDNS and HTTPS certificates enabled for the tailnet (Tailscale Serve needs both); without Tailscale, run the server yourself (end of [Install](#install)). git is optional: without it projects group by folder and no branch shows. Building needs nothing beyond Bun (see [Build](#build)).

- **Linux** (Arch, verified): a systemd user session. The service runs while you're logged in; `loginctl enable-linger $USER` keeps it running after logout and starts it at boot.
- **macOS** (verified on macOS 26, Apple Silicon): launchd. If `tailscale` isn't on `PATH`, the installer uses the App Store / standalone app's CLI at `/Applications/Tailscale.app/Contents/MacOS/Tailscale`.
- **Windows** (not run): Task Scheduler (`schtasks`), Windows Script Host (`wscript.exe`) and PowerShell, all built in. No admin rights: the task runs as you, at your logon. The extension is copied, not linked (symlinks need Developer Mode), so re-run the installer after updating the checkout; the list's banner says when the copy is stale.

## Install

```bash
bun install
bun run install-service           # = bun install.ts [--port N] [--dry-run]
bun install.ts --uninstall        # [--dry-run]
```

`install.ts` installs a per-user service for this checkout. In order, it:

1. builds `dist/` (`bun build.ts`);
2. puts the omp extension into `<omp dir>/extensions/tern-mobile.ts` (`~/.omp/agent` unless `TERN_AWUI_OMP_DIR`): a symlink to `omp-extension/tern-mobile.ts` on Linux and macOS, a copy on Windows, and links the Tern plugin in `tern-plugin/` (`tern plugin link`; uninstall runs `tern plugin unlink tern-awui`; a Tern without plugins only loses parking);
3. writes the service, with the absolute paths of bun and the checkout, a `PATH` starting with the folders of `tern`, `omp` and bun, the port and the allowed logins, and starts it (a re-run restarts it with the new settings):
   - Linux: `~/.config/systemd/user/tern-awui.service` (a real file; a symlink left there is replaced), `systemctl --user daemon-reload`, `enable`, `restart`; the unit starts bun through `<config dir>/tern-awui`, a symlink to it, so the process is named `tern-awui` and a rule for `bun` (ananicy-cpp's `BG_CPUIO`: nice 16, `SCHED_IDLE`) doesn't push it behind every agent; before writing it, the pre-0.3 `tern-mobile.service` is stopped, disabled and removed (uninstall removes it and the symlink too);
   - macOS: `~/Library/LaunchAgents/dev.tern-awui.plist` (`RunAtLoad`, `KeepAlive`, log in `~/Library/Logs/tern-awui.log`), `launchctl bootout` + `bootstrap gui/<uid>`;
   - Windows: a launcher `tern-awui.vbs` in the config dir that runs bun with no window and restarts it 3 s after it exits, and a scheduled task `tern-awui` that starts it at your logon at normal priority (`<Priority>5</Priority>`; the default 7 is below normal) (`schtasks /Create /XML`, then `/Run`);
4. runs `tailscale serve --bg --https=<port> http://127.0.0.1:<port>`;
5. prints the app's URL: `https://<this machine's tailnet name>:<port>/`.

The allowed login is the device's own Tailscale user (`tailscale status --json`) unless `TERN_AWUI_ALLOW` is set; the installer refuses to publish without one. `TERN_AWUI_HOSTS` is written as the device's tailnet name (Tailscale Serve keeps the browser's `Host`), followed by any names `TERN_AWUI_HOSTS` held when the installer ran. `TERN_AWUI_PORT` (or `--port`) and any of `TERN_AWUI_CONFIG`, `TERN_AWUI_OMP_DIR`, `TERN_AWUI_NOTES_DIR`, `TERN_AWUI_PROJECTS`, `TERN_AWUI_VAPID_SUBJECT` set when the installer runs are written into the service. `--dry-run` prints every file it would write (with its content) and every command, and changes nothing. `--uninstall` stops and removes the service, the extension link or copy (a link to another checkout's extension stays) and the serve entry; the config dir (tokens, VAPID keys, subscriptions) stays.

Relative config, omp and notes directories, and a `TERN_AWUI_PROJECTS` path containing a separator, are resolved before installation. The installed port is read back from `bridge.json` (when it belongs to this config dir): a re-install on another port turns the old `tailscale serve` port off, and `--uninstall` without `--port` or `TERN_AWUI_PORT` uses it. Uninstall removes bridge discovery only when it still matches this installation; missing optional cleanup commands are reported without stopping the remaining cleanup.

**Opening it.** Open the printed URL on the phone, signed in to Tailscale as an allowed login; in Chrome on Android, ⋮ → *Add to Home screen* installs it. Any device of an allowed login on the tailnet gets in, so there is nothing to pair.

omp loads extensions at startup, so omp sessions already running don't bridge until restarted (`/restart`). The app flags bridged sessions running an older extension and offers Reload (omp's `/restart`) where omp has it.

Without the installer (no Tailscale, or for development), run the server directly. Without `TERN_AWUI_ALLOW` it has no login check, so everything that can reach the port gets a shell (see [Security](#security)):

```bash
bun run build && TERN_AWUI_PORT=4381 bun server.ts
```

## Build

`bun run build` (`bun build.ts`) bundles `web/app.tsx` into `dist/` and copies the static files from `web/` and the prebuilt binaries from `assets/`; it needs no other tools. `assets/` is committed:

- `icon.svg`: the app icon (a "T" with a green dot) as a full-bleed tile.
- `icon-v2-32.png`, `icon-v2-180.png`, `icon-v2-192.png`, `icon-v2-512.png` (rounded corners) and `icon-v2-maskable-512.png` (the full tile, its mark inside Android's safe circle): favicon, Apple touch icon, PWA and notification icons rendered from it. The `v2` in the names makes browsers fetch new files when the icon changes.
- `symbols.woff2`: the private use areas of Symbols Nerd Font (`SymbolsNerdFont-Regular.ttf`, Nerd Fonts 3.5.1) subset by `pyftsubset`, for the Nerd Font icons in pane titles; its license is `assets/LICENSE-nerd-fonts-symbols` (SIL OFL 1.1 for the fonts, MIT for Nerd Fonts' code).

Build output is prepared in a temporary sibling directory. Compilation or missing-asset failures leave the previous `dist/` intact; replacement happens only after the new files are ready.

Each build gets an id, a hash of its files: `dist/build-id`, also baked into `app.js` (the build fails if any other file holds it). Rebuilding unchanged sources keeps the id. The server serves `dist/` from disk, so a rebuild needs no restart. It watches for the new `dist/` and sends its id with the list (`state.app`). An open page built from another id reloads itself, once its composer holds no unsent text or images.

Neither `Bun.serve` nor `tailscale serve` compresses, so the build writes a brotli copy (`<file>.br`, quality 9) beside every `.js`, `.css`, `.html` and `.webmanifest`, and the server sends it to browsers whose `accept-encoding` has `br` (`app.js`: 160 KB → 50 KB). `chunk-*.js` names are content hashes and go out `immutable` for a year; the symbols font is cached a week; everything else is `no-cache` with an `ETag` from the build id (`-br` suffixed for the brotli copy), so an unchanged build answers a reload with 304 and no body.

`bun run assets` (`bun assets.ts`) regenerates them after changing the icon or updating the font. It needs ImageMagick's `magick`, `pyftsubset` (fonttools with brotli) and the font at `/usr/share/fonts/TTF/SymbolsNerdFont-Regular.ttf` or `TERN_AWUI_SYMBOLS_FONT`. If `optipng` is installed, it and `bun docs/screenshots.ts` shrink the PNGs losslessly (`-o7 -strip all`); without it they write unoptimized PNGs.

## Tests

```bash
bun test
bun test --coverage
bun run typecheck
bun test test/e2e
```

The unit suites cover parsing, security boundaries and UI behavior. Preact tests render the chat, list, session and model-picker modules in happy-dom, including markdown, prompt actions, model selection and read-only subagents.

GitHub Actions (`.github/workflows/ci.yml`) runs the typecheck, the full suite with coverage including the browser tests (a fresh Playwright headless shell, required there rather than skipped) and the build on Linux. macOS and Windows jobs run the platform-dependent suites (`lib/`, `web/`, the extension and the installer, including the PowerShell checks on Windows) and the build; they report without blocking until they have passed natively.

Releases: new entries go under `## Unreleased` at the top of `CHANGELOG.md`. To release, rename that heading to `## X.Y.Z (YYYY-MM-DD)`, set `version` in `package.json`, commit as `X.Y.Z`, then push an annotated tag `vX.Y.Z` (`git tag -a vX.Y.Z -m "tern-awui X.Y.Z"`). `.github/workflows/release.yml` then publishes a GitHub release whose notes are that changelog section; a missing or empty section fails the run instead of publishing.

Server integration tests call `startServer({ env, home, dist, sendNotification })` in-process, so `bun test --coverage` measures `server.ts`. Each sandbox uses a temporary HOME, fake `tern` and `omp` executables, a random loopback port and fake bridge WebSocket clients. Push delivery is injected where tested. The harness can also run a subprocess for process-level checks. Installer tests exercise `main()` with temporary files and fake commands, covering install, uninstall, dry runs, configuration and command failures. macOS and Windows installer paths are tested as plans, not native service installations.

The browser suites use `playwright-core` with headless Chromium at phone size, 412×900, and desktop size, 1400×900. Set `TERN_AWUI_CHROMIUM` to its executable, or use an existing `~/.cache/ms-playwright/chromium_headless_shell-*/chrome-headless-shell-linux64/chrome-headless-shell`; the newest cached revision wins. The suites skip if neither exists. They do not download a browser.

Browser tests run `build.ts` in a temporary checkout directory and serve its temporary `dist/`. They do not rebuild the live app's assets. Requests carry the allowed `tailscale-user-login` header, service workers are blocked, and page requests cannot leave the sandbox server. Tests assert rendered content, navigation and the actions received by the fake bridge and CLI, including drafts, sends, asks, models, rewind, live text and subagents. They never connect to the live `tern-mobile` service or real Tern panes. Chromium execution is outside Bun's coverage instrumentation, so browser-exercised UI lines do not contribute to the Bun coverage report.

`TERN_AWUI_LIVE=1 bun test omp-extension/tern-mobile.live.test.ts` opts into the real omp bridge test. It uses temporary HOME/config directories and a dummy credential, without model prompts; explicit opt-in fails if omp is missing. PowerShell process-selection tests skip when `pwsh` is unavailable. Permission-denied filesystem scenarios skip when run as root. These skips do not verify native Windows services, macOS services or real push delivery.

## Security

This is a remote shell into the desktop, and it has **no authentication of its own**. Access control belongs to whatever stands in front of the port; the server only makes sure that "loopback only" means that, and offers one optional identity check for Tailscale.

Out of scope, by design:

- **Who reaches the port.** The server listens only on `127.0.0.1`. Keeping it on loopback, or publishing it through Tailscale Serve (what the installer does), Cloudflare Access, an SSH tunnel or similar, is the user's choice and the user's responsibility. **Never enable Funnel** or forward the port publicly.
- **Other local accounts.** Any account on the machine can connect to `127.0.0.1` and set any header. The machine must be single-user.

Built in:

- **Host check (DNS rebinding).** Every request, the bridge's too, must name `localhost`, `127.0.0.1`, `[::1]` or a `TERN_AWUI_HOSTS` entry in `Host` (any port, case and a trailing dot ignored); anything else, or no `Host`, gets 403. Without it, a web page that rebinds its own domain to 127.0.0.1 would count as same-origin in the user's browser and could set every header below.
- **Same-origin POSTs.** POSTs require an `x-tern-mobile: 1` header; a cross-site page can't send it without a CORS preflight, which the server never approves. Key names are allowlisted.
- **Bridge token.** `/bridge` refuses requests carrying a Tailscale login header (anything proxied from outside) and requires the bridge token (`<config dir>/bridge-token`, mode 600). Browsers can't set that header on a WebSocket, so no page can pose as an omp session.
- **Optional Tailscale login allowlist.** With `TERN_AWUI_ALLOW` set, every request (the API, its stream and the app's own files) must carry an allowed `Tailscale-User-Login`, else 403; tagged devices get no login header, so they are refused. The header is trusted as-is: it means something only when Tailscale Serve (or a proxy that overwrites it) is the only way in. Without `TERN_AWUI_ALLOW` there is no login check and the startup log says so.
- tern can report errors with exit status 0, so non-WARN stderr counts as failure and is returned to the phone. Typed text goes after `--`, so text like `--help` is typed, not read as tern's flags.
- Agent markdown goes through DOMPurify. Only `http(s)` and `mailto` links are kept, and raw HTML is shown as text.
- Responses carry a Content-Security-Policy (`default-src 'self'`, images also `data:`/`blob:`, inline styles allowed for mermaid): images agent markdown points to on other sites are never fetched, so a prompt injection can't leak data through an image URL.
- Texts sent for a block (prompts, drafts, completions) are capped at 1,000,000 characters; Bun closes bridge frames over 16 MB.

## Limits

- It is not a terminal emulator. Full-screen TUIs (vim, htop) only work through the screen capture and the key bar.
- Status, chat, model picks and images need the omp to be connected to the bridge: omp sessions started before the extension's current version show as terminals until restarted (`/restart`).
- Features the session's omp lacks (the extension reports them as `caps`) are turned off in the app, and the server refuses Rewind, the model catalog and tier changes for them with 409. An extension without `caps` (before versioning) is taken to support everything, as before.
- Linux and macOS have run this; Windows hasn't. omp's directory on macOS is verified; Tern's notes folder on macOS and both locations on Windows follow their sources (omp's directory resolver, the strings in the tern binary) and are unverified. `TERN_AWUI_OMP_DIR` and `TERN_AWUI_NOTES_DIR` set them by hand. omp profiles (`OMP_PROFILE`) are not followed.
- Only main sessions bridge (`ctx.agent.kind === "main"`). Older extension versions also bridged subagents under the same pane, which took over the pane's status (idle while the main session still worked) and, on exit, unbridged it; the server now keeps every connection per pane and hands the pane back to the remaining one (`sync`).
- omp's own retries of a rate limit run before the turn stops; the usage-limit banner appears only after omp gave up. A deny's reason and a usage-limit continue need the extension at protocol 6: a session started before it must restart.
